# bench — 벤치 하네스

`mgit-bench` 는 모드가 다섯이다. `repos/` 는 gitignore 대상이다.

- 저장소 모드(`--repo`): 명세 5절 PoC-1(대형 저장소 그래프)을 잰다. `--filters` 면 대신 해시 패스의 추가 시간을 잰다 (W18).
- 폴더 모드(`--folder`): 저장소 여러 개가 든 폴더를 여는 경로를 잰다 (W0 측정 기준선, W18 측정 포함).
  `--memory` 면 메모리 분해만, `--lanes` 면 화면당 레인 수 분포만 잰다 (W18).
- 파일 트리 모드(`--fs`): 큰 디렉터리 나열과 1 MiB 파일 읽기의 코어 쪽 시간 (W18).
- stage 모드(`--stage`): 변경 파일이 많은 저장소의 폴더 stage·unstage 와 그 뒤 부분 갱신 (W18).
- tags 모드(`--tags`): 원격 tag 조회·비교·보고서 크기, `RefsChanged` 기준선, 일괄 push·원격 삭제 (TG-17, B4).

벤치는 릴리스로 빌드해 바이너리를 바로 돌려도 된다(`cargo build --release -p mgit-bench` → `./target/release/mgit-bench …`).

화면(프런트) 렌더링은 `frontend-measure.js`(브라우저 페이지 안에서 돌리는 측정 도구)로 잰다 — 맨 아래 "W18 ② 화면 측정" 절.

tag 관리 측정(TG-17)의 저장소·원격은 `setup.sh tags` 로 만들고 `--tags` 로 잰다 — 맨 아래 "tags 픽스처" 절.

## 저장소 모드 — PoC-1 그래프 로드

### 준비

```bash
bench/setup.sh git          # git/git clone + commit-graph write (약 8.6만 커밋)
bench/setup.sh rust         # rust-lang/rust (약 34.5만 커밋)
bench/setup.sh linux        # torvalds/linux (100만 커밋 이상)
bench/setup.sh folder 1 200000   # 합성 단일 저장소 20만 커밋 → repos/folder-1x200000/repo-01 (122MB, W18)
```

### 실행

```bash
cargo run --release -p mgit-bench -- --repo bench/repos/git            # commit-graph 사용
cargo run --release -p mgit-bench -- --repo bench/repos/git --no-commit-graph   # -c core.commitGraph=false
cargo run --release -p mgit-bench -- --repo bench/repos/git --filters  # 해시 패스 추가 시간 (W18)
```

옵션: `--window N`(기본 500), `--runs N`(기본 3).

| 출력                         | 재는 것                                                                                      |
| ---------------------------- | -------------------------------------------------------------------------------------------- |
| `first_chunk`                | `Core::open_repo` 호출부터 `GraphFirstChunk`(500행)까지 — 저장소 탭의 첫 그래프 창 (코어 쪽) |
| `finished`                   | 같은 시작부터 `GraphLoadFinished` 까지                                                       |
| `window_top`·`window_mid`    | 로드가 끝난 뒤 `graph_window(0, 500)` 과 가운데 범위 조회 한 번 — 창 조회                    |
| `lanes`·`segments≈`·`edges`  | 전체 레이아웃의 레인 수, 구간 수(청크 경계에서 중복 계산되는 근사치), 엣지 수                |
| `rss=a→b`                    | 실행 전·후의 프로세스 RSS. 한 프로세스에서 이어 돌리므로 2회차부터는 앞 실행의 몫이 남는다   |
| 요약 JSON `*_min`·`*_median` | 실행들의 최솟값(PoC-1 판정)과 중앙값(W18 부터, 폴더 모드 표와 같은 통계)                     |

### 통과 기준

- commit-graph 있음 기준 커밋 10만 개 첫 화면(`GraphFirstChunk`) 1초 이하
- RSS 500MB 이하

## 폴더 모드 — 여러 저장소 폴더 열기 (W0 측정 기준선)

폴더를 열고(`open_folder`) 요약을 읽고(`folder_summaries`) 브랜치 목록을 읽고(`folder_branches`, W6 부터)
통합 타임라인을 여는 경로를 잰다. 제품이 부르는 순서와 같다.
이후 슬라이스(W6·W9·W18)는 아래 기준 수치와 비교한다.

### 준비

```bash
bench/setup.sh folder            # 저장소 20개 × 저장소당 커밋 1만 개 → repos/folder-20x10000 (약 12초, 114MB)
bench/setup.sh folder 50 10000   # 저장소 수·저장소당 커밋 수 지정 → repos/folder-50x10000 (284MB)
bench/setup.sh remotes           # 원격 브랜치가 많은 저장소(W9): folder-20x10000/repo-01 복사 + 원격 추적 ref 300개 → repos/remotes-300
bench/setup.sh remotes 800 repos/folder-20x10000/repo-05   # ref 수·원본 저장소 지정
# W18
bench/setup.sh folder 20 2000 partial      # 커밋 시각 배치 uniform(기본)|partial|clustered → repos/folder-20x2000-partial (27MB)
bench/setup.sh folder 1 200000             # 깊은 이력 단일 저장소 → repos/folder-1x200000 (122MB)
bench/setup.sh remotes 300 repos/folder-1x200000/repo-01 remotes-300-deep       # + 원격 300 → repos/remotes-300-deep (111MB)
bench/setup.sh folder 1 400000             # → repos/folder-1x400000 (228MB)
bench/setup.sh remotes 300 repos/folder-1x400000/repo-01 remotes-300-deep400    # → repos/remotes-300-deep400 (219MB)
bench/setup.sh fs 50000                    # 파일 트리: big/ 빈 파일 5만 개 + file-1m.txt(정확히 1 MiB) → repos/fs-50000
bench/setup.sh stage 5000                  # 추적 파일 5천 개가 모두 수정된 저장소 → repos/stage-5000 (21MB)
```

시각 배치(W18 레인 측정): 저장소 하나의 활동 기간은 최대 커밋 수 × 480초(W)다. `uniform` 은 모든 저장소가 같은 기간에 활동해
고르게 섞이고(W0 부터의 스트림 그대로), `partial` 은 저장소마다 W/4 씩 밀어 어느 시점이든 3~4개가 겹치고, `clustered` 는 W 씩 밀어
겹치지 않는다(번호가 큰 저장소가 최근). `remotes` 의 셋째 인자는 결과 폴더 이름이다(주지 않으면 `remotes-<수>`).

`git fast-import` 로 만드는 합성 저장소다. 날짜·작성자가 고정이라 같은 인자면 항상 같은 커밋이 나온다.
이미 있는 저장소는 건너뛰므로 다시 만들려면 폴더를 지운다. 저장소 하나의 구성:

- main 한 줄기. main 커밋 400개마다 토픽 브랜치(3커밋)를 main 과 번갈아 쌓고 머지한다 (1만 커밋이면 머지 24개)
- 머지하지 않은 로컬 브랜치 2개(`feature/search`, `feature/login`)
- 원격 추적 브랜치 4개: `origin/main`(main 기준 ahead 5·behind 1), `origin/feature/login`, `origin/hotfix`(원격에만 있음), `origin/release/1.0`
- 모든 ref 에서 닿는 커밋 수가 정확히 지정한 수다. 커밋 시각은 저장소마다 간격이 달라 타임라인에서 서로 섞인다
- commit-graph 있음. 작업 트리는 파일 60여 개(1만 커밋 기준)로 작고 깨끗하다

### 실행

```bash
cargo run --release -p mgit-bench -- --folder bench/repos/folder-20x10000
cargo run --release -p mgit-bench -- --folder bench/repos/folder-20x10000 --no-commit-graph
cargo run --release -p mgit-bench -- --folder bench/repos/folder-20x10000 --memory         # 메모리 분해 (W18, macOS)
cargo run --release -p mgit-bench -- --folder bench/repos/folder-20x2000-partial --lanes   # 화면당 레인 수 (W18)
cargo run --release -p mgit-bench -- --fs bench/repos/fs-50000 --runs 5                     # 파일 트리 (W18)
cargo run --release -p mgit-bench -- --stage bench/repos/stage-5000                         # 폴더 stage·unstage (W18)
```

옵션: `--runs N`(기본 3). 실행마다 코어를 새로 만들어 아래를 순서대로 재고, 끝에 중앙값과 합격선 대비를 출력한다.

| 출력               | 재는 것                                                                                            |
| ------------------ | -------------------------------------------------------------------------------------------------- |
| `open_folder`      | `Core::open_folder` 호출부터 반환까지. 하위 저장소 스캔, 저장소별 판별, `.git` 감시 등록 포함      |
| `summaries`        | `Core::folder_summaries` 호출부터 반환까지 (저장소 전부의 status·진행 중 작업·마지막 fetch)        |
| `branches`         | `Core::folder_branches` 호출부터 반환까지 (저장소 전부의 HEAD·ref, `log` 없음)와 합친 브랜치 수    |
| `timeline`, `rows` | `Core::folder_timeline_open` 호출부터 `GraphLoadFinished` 수신까지와 그때의 행 수                  |
| `rss_peak`         | 측정 구간 동안 5ms 간격으로 읽은 프로세스 RSS 의 최댓값 (MiB)                                      |
| `git_cmds`         | 코어 명령 로그에 기록된 git 실행 수 (구간별)                                                       |
| `contains <대상>`  | 타임라인 뒤 경로순 첫 저장소에서 `Core::folder_commit_containing_refs` 한 번의 시간·결과 (W9)      |
| `light_session`    | 같은 첫 저장소의 `Core::folder_open_repo_session` 한 번과, 비교로 그 저장소의 `open_repo` (W13)    |
| `filter <경우>`    | 위 측정이 모두 끝난 뒤 따로 `--runs` 번: 필터 질의·저장소 범위를 바꾼 때부터 재로드 완료까지 (W16) |
| `authors <출처>`   | 같은 필터 측정 안에서 `Core::folder_timeline_authors` 한 번 (테이블에서 / git 으로) (W16)          |
| `discover`         | 기본 측정의 구간별 저장소 판별(`rev-parse --show-toplevel …`) 수와 명령 로그 실행 시간 합 (W18)    |
| `w18 run`          | 필터 측정 뒤 따로 `--runs` 번: 전체 갱신 한 번, 커밋 상세 첫·다음 요청, ref 변경 → 갱신 (W18)      |
| `contains burst`   | 같은 W18 측정 안에서 포함 브랜치를 5번 250ms 간격으로 요청 (커밋을 빠르게 옮길 때, W18)            |
- 코어는 데스크톱 셸처럼 `NotifyWatcher` 를 단다. 저장소는 `MemoryStore` 라 사용자 DB 를 건드리지 않는다.
- `git_cmds` 에 러너 초기화 때의 2회(`--version`, `rev-parse --local-env-vars`)는 들어가지 않는다.
- 요약의 `rss_peak_mb_max` 는 연속 실행 전체의 최댓값이다. 한 프로세스에서 이어 돌리면 할당자가 쥐고 있는 메모리 때문에
  2회차부터 약 10% 높게 나온다. 폴더를 한 번 여는 값은 run 1 이다. 커널이 잰 최고치는 `/usr/bin/time -l` 로 대조한다.
- 판정 줄의 합격선은 조건이 정해져 있다(아래 표). 다른 크기의 폴더에서 나온 ok/over 는 참고값이다.

릴리스 빌드, `--runs 3` 의 중앙값(RSS 는 최댓값). 페이지 캐시가 데워진 상태이고, 다른 작업이 함께 돌던 기기에서 쟀다(load average 4~6).

읽는 법과 한계:

- 흔들림: 같은 날 `folder-20x10000` 를 6묶음(각 3회) 돌린 중앙값이 open_folder 105~140ms, summaries 52~65ms,
  timeline 436~538ms, RSS 최대 129~138MB 였다. 이 폭 안의 차이는 변화로 보지 않는다.
- `rss_peak` 는 `/usr/bin/time -l` 의 `maximum resident set size` 와 1.5% 이내로 맞았다(20만 행 131MB, 50만 행 356MB).
- git 명령은 저장소당 10개다. open 1(`rev-parse` 판별), 요약 2(판별, `status`),
  타임라인 7(판별 2, `symbolic-ref`, `rev-parse HEAD`, `for-each-ref`, `remote`, `log`). 판별이 세 구간에 걸쳐 저장소당 4번 돈다.
- `folder-50x10000` 의 RSS 356MB 는 50만 행 값이라 합격선(20만 행 300MB)과 견주지 않는다.
- 작업 트리가 작아 `status` 비용이 실제 저장소보다 낮다. 요약 수치는 하한으로 본다.
- 페이지 캐시가 식은 상태(재부팅 직후 첫 열기)는 재지 않았다.
- 출력의 `truncated` 가 저장소 수와 같게 나온다. 저장소당 커밋이 타임라인 상한(`timeline_max_per_repo` 1만)과 정확히 같아서이고, 잘린 커밋은 없다.

### 2026-11-18 W9 포함 브랜치 (`for-each-ref --contains`)

- `oldest`: main 의 루트 커밋 — 거의 모든 브랜치가 품는다
- `newest`: main 끝 — 몇 개만 품는다
- `side`: 머지하지 않은 `feature/search` 끝 — HEAD(main)에서 닿지 않아 HEAD 확인(`merge-base --is-ancestor`)이 한 번 더 돈다

`remotes-300` 은 `bench/setup.sh remotes` 로 만든다: `folder-20x10000/repo-01` 을 복사하고 `refs/remotes/origin/bench/feature-NNNN`
300개가 main 첫 부모 이력을 고르게 나눈 과거 커밋을 가리키게 한다(원래 원격 4개 + 300 = 304, 로컬 3).

읽는 법과 한계:

- git 명령은 HEAD 의 현재 브랜치가 그 커밋을 품으면 1개(`for-each-ref --contains`), 아니면 2개다. 측정값이 그대로 맞았다.

  최근 커밋에 몰린 경우)와 아주 큰 저장소(수십만 커밋)는 재지 않았다. `git/git`(8.6만 커밋)도 이번에는 재지 않았다.
- 페이지 캐시가 식은 상태는 재지 않았다. `--contains` 는 저장소 하나에서만 돌므로 저장소 수와는 무관하다.

### 미뤄 둔 항목

#### 전체 갱신 한 번 (창 포커스·60초 주기·새로고침)

프런트의 `reload('all')` 처럼 요약 + 브랜치 목록 + 변경 목록을 동시에 부른다.

| 폴더                                | 시간  | git 명령                             | `status` | 판별 |
| ----------------------------------- | ----- | ------------------------------------ | -------- | ---- |
| `folder-20x10000`                   | 172ms | 180 (요약 40 / 변경 40 / 브랜치 100) | 40       | 60   |
| `folder-20x10000 --no-commit-graph` | 174ms | 180                                  | 40       | 60   |
| `folder-50x10000`                   | 404ms | 450                                  | 100      | 150  |

저장소당 `status` 2번(요약·변경), 판별 3번(요약·변경·브랜치). 2초 대비 여유가 11배(20개)·5배(50개)라 "요약과 변경이 status 한 번을
나눠 쓰기"는 넣지 않았다. 합성 저장소는 작업 트리가 파일 60여 개로 작아 `status` 가 실제보다 싸다(하한).

#### 저장소 판별 중복

판별은 지금도 기본 경로에서 저장소당 4번(open·요약·브랜치·타임라인), 전체 갱신마다 3번 더 돈다. `discover` 출력(명령 로그의 실행 시간 합):

| 구간          | 20개: 수 · 합 | 50개: 수 · 합 | 비고                                                            |
| ------------- | ------------- | ------------- | --------------------------------------------------------------- |
| `open_folder` | 20 · 92ms     | 50 · 280ms    | 저장소를 차례로 판별한다 — open 시간(116ms / 333ms)의 79% / 84% |
| 요약          | 20 · 127ms    | 50 · 257ms    | 동시 8개라 벽시계 몫은 합보다 작다                              |
| 브랜치 목록   | 20 · 94ms     | 50 · 236ms    | 〃                                                              |
| 타임라인      | 20 · 125ms    | 50 · 381ms    | 〃                                                              |

`open_folder` 가 50개에서도 333ms 라 "판별 결과 재사용"은 넣지 않았다. 넣는다면 효과가 큰 곳은 재사용보다 `open_folder` 의 차례
판별을 동시에 도는 것이다(추정, 재지 않음).

#### 저장소 1개 ref 변경 → 갱신

W18 측정이 경로순 첫 저장소에 빈 커밋을 가리키는 브랜치(`refs/heads/bench/w18-ref-change`)를 만들고(벤치가 git 을 직접 돌린다) 잰다.
끝나면 지운다.

| 폴더                                                      | 감시 이벤트 | 부분 갱신 (그 저장소만)     | 타임라인 재로드 (전체 재병합) | 판정            |
| --------------------------------------------------------- | ----------- | --------------------------- | ----------------------------- | --------------- |
| `folder-20x10000`                                         | 197ms       | 59ms, git 9 (다른 저장소 0) | 358ms, git 120                | 통과            |
| `folder-50x10000`                                         | 200ms       | 35ms, git 9 (다른 저장소 0) | 883ms, git 300                | 통과 (여유 12%) |
| `remotes-300-deep400` (단일 40만 커밋, commit-graph 없음) | 197ms       | 83ms                        | 1,286ms, git 6                | 조건 밖 (참고)  |
- 감시 이벤트는 `update-ref` 직후부터 그 저장소의 `FolderChanged{refs: true}` 까지(FSEvents + 감시 디바운스 150ms). 프런트는 그 뒤
  부분 갱신을 400ms, 타임라인 재로드를 1.5초 디바운스한 뒤 부른다. 판정은 디바운스 뒤의 일 중 늦은 쪽이다.
- 부분 갱신은 그 저장소에서만 git 이 돈다(명령 로그의 cwd 로 확인). 타임라인은 저장소 전부를 다시 읽고 다시 병합한다 — 20개는 여유가
  커서 "타임라인 증분 재병합"은 넣지 않았다. 50개는 1초에 가깝다(조건 밖).
- 새 커밋은 재로드한 타임라인에 들어온다(`new_commit_found=true`). 저장소당 커밋이 상한(1만)이라 가장 오래된 커밋이 대신 빠져 행 수는 같다.
- 커밋이 40만 개이고 commit-graph 가 없는 저장소 하나는 그것만으로 타임라인 로드가 1.3초다(`log --date-order` 가 이력 전체를 걷는다).
  commit-graph 가 있으면 289ms 다.

#### 메모리 분해 (`--memory`)

`folder-20x10000`, 단계마다 새 프로세스, 중앙값 3회. RSS 는 프로세스 상주 크기, 힙은 `vmmap -summary` 의 malloc 할당 바이트(살아 있는
할당만), footprint 는 `vmmap` 의 physical footprint(활성 상태 보기의 "메모리" — 할당자가 재사용 표시한 해제 페이지는 빠진다).

| 단계 · 값                                             | RSS                   | 힙        | footprint                |
| ----------------------------------------------------- | --------------------- | --------- | ------------------------ |
| 정상 상태 (20만 행 읽은 뒤)                           | 95MB                  | 38MB      | 60MB                     |
| 첫 로드 최댓값                                        | 116MB                 | —         | 110MB (최고)             |
| 같은 질의 재로드 최댓값                               | 151MB                 | 38MB (뒤) | 116MB (최고)             |
| 옛 데이터가 작은 재로드 (1만 → 20만 행) 최댓값        | 118MB                 | —         | 111MB (최고)             |
| `text_few` (60행) / `hash` (1행) / `text_many` 최댓값 | 101MB / 116MB / 150MB | —         | 112 / 115 / 117MB (최고) |
| 닫고 코어를 버린 뒤                                   | 119MB                 | 0.3MB     | —                        |

벤치가 저장소마다 타임라인과 같은 `git log` 를 따로 돌려 센 크기: 출력 합 29.6MiB(동시 8개 최대 11.8MiB), 파싱한 레코드 힙 어림
66.9MiB(커밋당 351B).

- 옛 데이터와 새 데이터가 함께 있는 몫: 같은 새 데이터를 만드는 두 재로드의 차(151 − 118) = 약 33MB. 정상 상태의 힙(38MB)과 맞는다.
- 저장소별 출력 버퍼·레코드: 병합이 끝날 때까지 20개 저장소의 레코드(약 67MiB)가 모두 살아 있다. 첫 로드 최댓값(116MB)이 정상
  상태(95MB)보다 높은 몫이 이것이다.
- 해시 패스: 결과 수가 비슷한 `text_few` 보다 15MB 높다 — 저장소마다 두 번째 로그의 출력 버퍼(동시 8개 11.8MiB)와 맞는다.
- 할당자가 돌려주지 않은 메모리: 한 프로세스에서 필터 → 되돌리기를 이어 재로드하면 힙은 38~45MB 그대로인데 RSS·footprint 가 오른다.

  | 재로드 횟수 | 2   | 12  | 20  | 40  | 50  | 60  |
  | ----------- | --- | --- | --- | --- | --- | --- |
  | RSS (MB)    | 160 | 246 | 306 | 260 | 313 | 283 |
  | footprint   | 93  | 179 | 239 | 172 | 226 | 194 |
  | 힙          | 38  | 39  | 39  | 41  | 41  | 41  |

  (한 프로세스 한 번: `MGIT_BENCH_REPEAT_PAIRS=30 ./target/release/mgit-bench --folder bench/repos/folder-20x10000 --memory-phase repeat`.
  `--memory` 의 `repeat` 단계는 6쌍 = 12번이다.)
  `vmmap` 로 보면 늘어난 것은 `Malloc Large (empty)`(해제한 큰 블록을 macOS 할당자가 캐시한 영역)다: 3개 11.8MB → 81개 127.6MB(12번째,
  `MGIT_BENCH_VMMAP_DIR=<폴더>` 를 주면 측정점마다 `vmmap -summary` 전체 출력을 남긴다).
  할당자가 가끔 비워 RSS 는 최대 327MB, footprint 는 최대 240MB 사이를 오르내린다. 닫고 코어를 버리면 힙이 0.3MB 로 돌아가므로 누수는
  아니다(힙의 완만한 증가 38 → 41MB 는 벤치가 명령 로그를 무제한으로 남긴 몫이다 — 제품은 500개).
- W16 의 240~329MB 는 한 프로세스에서 코어 6개·재로드 39번이 이어진 값이라 위 "할당자 보유"와 같은 현상이다. 새 프로세스의 재로드
  한 번은 151MB 다.
- 판정: 합격선(20만 행 정상 상태 300MB) 통과 — RSS 95~134MB, footprint 60MB. 긴 세션에서 재로드를 수십 번 반복하면 RSS 가 300MB 를
  넘을 때가 있다(footprint 는 240MB 아래). 살아 있는 데이터가 아니라 할당자 캐시라 고치지 않았다.

#### 포함 브랜치 (`for-each-ref --contains`)

원격 추적 브랜치 304개 + 로컬 3개. `remotes-300-deep` 은 20만, `remotes-300-deep400` 은 40만 커밋 저장소의 복사본이다.

| 픽스처 · 조건                           | oldest (307개) | newest (3개) | side (1개, git 2) |
| --------------------------------------- | -------------- | ------------ | ----------------- |
| `remotes-300-deep`                      | 571ms          | 15.5ms       | 18.3ms            |
| `remotes-300-deep --no-commit-graph`    | 890ms          | 899ms        | 903ms             |
| `remotes-300-deep400`                   | 1,180ms        | 17.0ms       | 20.4ms            |
| `remotes-300-deep400 --no-commit-graph` | 1,866ms        | 1,909ms      | 1,893ms           |
- `remotes-300-deep --no-commit-graph` 는 7회(표본 21개) 879~924ms 였다. 부하가 높을 때(load average 3~4) 1,050ms 가 한 번 나왔다.
- commit-graph 가 있어도 모든 브랜치가 품는 오래된 커밋은 이력 깊이에 비례한다(20만 571ms → 40만 1,180ms). 없으면 대상과 무관하게

- 40만에서 1초를 넘어 "세션마다 마지막 요청만 살리기"를 넣었다(아래 "고친 항목").

#### 레인 수와 그래프 열 폭 (`--lanes`)

`folder-20x2000`(uniform)·`-partial`·`-clustered`, 각 4만 행. 화면 = 연속 50행. 화면의 레인 수는 그래프 뷰가 열 폭을 정하는 방식
(그 범위의 행 노드·구간 레인의 최댓값 + 1)과 같게 셌다. 열 폭 = min(레인, 24) × 14 + 8 px. 긴 엣지 접기 거리 N 은 벤치 안에서만
바꿨다(제품 기본 40).

| 배치      | N       | 전체 레인 | 화면당 p50 / p90 / 최대 | 열 폭 p50 / p90 / 최대 | 13레인 넘는 화면 | 50행당 스텁 |
| --------- | ------- | --------- | ----------------------- | ---------------------- | ---------------- | ----------- |
| uniform   | 40      | 22        | 21 / 22 / 22            | 302 / 316 / 316px      | 99.9%            | 0           |
| uniform   | 20      | 17        | 12 / 15 / 17            | 176 / 218 / 246px      | 14.5%            | 42          |
| uniform   | 10      | 10        | 1 / 4 / 10              | 22 / 64 / 148px        | 0%               | 100         |
| uniform   | 5       | 5         | 1 / 1 / 5               | 22 / 22 / 78px         | 0%               | 100         |
| partial   | 40      | 6         | 4 / 4 / 6               | 64 / 64 / 92px         | 0%               | 0           |
| partial   | 20·10·5 | 5         | 4 / 4 / 5               | 64 / 64 / 78px         | 0%               | 0           |
| clustered | 40      | 4         | 3 / 3 / 4               | 50 / 50 / 64px         | 0%               | 0           |
| clustered | 20      | 3         | 1 / 2 / 3               | 22 / 36 / 50px         | 0%               | 0           |
| clustered | 10      | 2         | 1 / 2 / 2               | 22 / 36 / 36px         | 0%               | 0           |
| clustered | 5       | 2         | 1 / 1 / 2               | 22 / 22 / 36px         | 0%               | 0           |
- 넓은 열(약 300px)은 모든 저장소가 같은 기간에 고르게 커밋할 때(uniform, `folder-20x10000` 도 레인 22)만 나온다. 활동 기간이 겹치는
  저장소가 3~4개면 화면당 4레인(64px), 겹치지 않으면 3레인이다. 레인 수는 "접기 거리 안에서 함께 활동하는 저장소 수"를 따른다.
- 접기 거리를 줄이면 uniform 은 레인 대신 끊긴 선(스텁)이 된다: N=20 에서도 화면당 12레인에 50행당 스텁 42개, N=10 이면 모든 행이
  스텁이다. partial·clustered 는 거의 그대로다. 현실적인 배치에서 넓게 나오지 않고 낮춰도 얻는 것이 없어 타임라인 전용 임계값은
  넣지 않았다.
- 참고: 폴더 로그의 모든 열(저장소 띠·제목 최소·작성자 최소·날짜·해시)이 들어가려면 로그 폭이 614px + 그래프 열 폭이어야 한다
  (`GraphRow.tsx` 의 열 폭 상수로 계산). 실제 창에서 열이 빠지는지는 W18 ② 의 몫이다.

#### 폴더 stage·unstage (`--stage`)

`stage-5000`(추적 파일 5천 개가 모두 수정됨), 중앙값 3회. 부분 갱신은 그 저장소만 요약 + 브랜치 + 변경을 동시에 읽는다.

| 동작                                | 시간                  | git 명령 |
| ----------------------------------- | --------------------- | -------- |
| 변경 목록 읽기 (5,000개)            | 144ms (첫 회 33ms)    | 2        |
| stage 전부                          | 493ms (첫 회 2,324ms) | 3        |
| 그 뒤 부분 갱신                     | 32ms                  | 8        |
| unstage 전부                        | 39ms                  | 3        |
| 그 뒤 부분 갱신                     | 191ms                 | 8        |
| 디렉터리 하나(50개) stage / unstage | 26ms / 19ms           | 3 / 3    |
| 파일 하나 stage / unstage           | 19ms / 17ms           | 3 / 3    |
- 첫 stage 전부는 `git add` 가 새 내용의 blob 5,000개를 처음 쓰는 비용이다(같은 내용을 다시 stage 하는 2회차부터 493ms).
- unstage 뒤의 `status` 가 느린 것(191ms, 그 뒤 변경 목록도 144ms)은 `restore --staged` 가 색인 항목의 stat 정보를 HEAD 트리에서 다시 만들어
  다음 `status` 가 파일 내용을 다시 비교하기 때문이다(git 동작).
- 합격선은 없다. 폴더 요약의 2초에 견주면 stage 전부 + 부분 갱신 525ms(첫 회 2.35초)다. 고치지 않았다.

### 고친 항목 — 포함 브랜치: 세션마다 마지막 요청만 살리기

- 원인(측정): 40만 커밋 × 원격 304개에서 `for-each-ref --contains` 한 번이 1.2초(commit-graph 있음, oldest)~1.9초(없음)다. 프런트는
  커밋을 옮길 때마다(디바운스 200ms) 새로 묻고 옛 응답은 버리지만, 코어는 옛 요청의 git 을 끝까지 돌렸다.
- 수정: 코어가 세션마다 마지막 요청의 취소 토큰을 기억하고(`inspect.rs` 의 `LatestRequests`), 같은 세션의 새 요청이 오면 앞 요청의
  토큰을 취소한다. 러너가 그 git 을 끝내고 거둔 뒤 앞 요청은 `CoreError::Cancelled`(기존 오류)로 끝난다. W9 의 시간 상한·취소
  방식(`containing_branches` 의 토큰)을 그대로 쓰고, 토큰을 호출자가 넘기는 `containing_branches_with` 를 더했다. 열쇠는 요청을 받은
  세션이다 — 폴더는 폴더 세션 하나다(저장소가 달라도 폴더의 상세 칸 하나가 차례로 묻고, 통합 타임라인은 이웃한 행의 저장소가 자주
  바뀌어 저장소별로 나누면 서로 끊지 못한다). IPC·프런트는 그대로다.
- 전후 (`remotes-300-deep400 --no-commit-graph`, 5번 250ms 간격, `contains burst`, 중앙값 3회):

  | 값                                 | 전       | 후      |
  | ---------------------------------- | -------- | ------- |
  | 마지막 요청 → 결과                 | 2,082ms  | 1,919ms |
  | 첫 요청 → 모두 끝                  | 3,084ms  | 2,920ms |
  | 끝까지 돈 / 취소된 `--contains`    | 5 / 0    | 1 / 4   |
  | `--contains` 프로세스 실행 시간 합 | 10,358ms | 2,921ms |

  요청 하나의 시간(1.2~1.9초)은 git 의 비용이라 그대로다. 줄어드는 것은 겹쳐 도는 프로세스(읽기 permit 8개·CPU)다.
  commit-graph 가 있으면 대상(`main~1…5`)이 최근이라 요청이 겹치지 않는다(취소 0, 프로세스 시간 합 192ms).
- 테스트: `mgit-core/tests/containing_latest.rs` (같은 세션의 새 요청이 앞 요청의 git 을 끝냄, 폴더는 저장소가 달라도 끊음, 다른 세션은
  끊지 않고 버린 요청은 자리를 남기지 않음 — 느린 `--contains` 를 흉내 내는 가짜 git).

## tags 픽스처 — tag 관리 (TG-17)

tag 관리 기능의 성능 측정(B4: 원격 tag 조회·파싱·비교 시간, 보고서 JSON 크기, `RefsChanged` 기준선, 일괄 push·삭제 청크,
트리 3,000 개 렌더링)에 쓸 작업 저장소와 bare 원격이다. 측정은 `mgit-bench --tags`(아래 "실행")이고, 트리 렌더링은 따로 잰다.

### 준비

```bash
bench/setup.sh tags          # tag 이름 1천 개 → repos/tags-1000 (repo-01 + origin.git)
bench/setup.sh tags 10000    # → repos/tags-10000
bench/setup.sh tags 50000    # → repos/tags-50000
```

N 은 tag 이름 수(로컬·원격의 합집합)이고 20~100,000 이다. `git fast-import` 로 만들고 날짜·작성자가 고정이라 같은 N 이면 항상 같은
객체가 나온다. 이미 있으면 다시 만들지 않고 개수만 찍는다(다시 만들려면 폴더를 지운다). `repos/tags-<N>/` 의 구성:

- `origin.git`: bare 원격. `repo-01` 의 원격 `origin` URL 이 이 폴더의 절대 경로라 조회·push 가 네트워크를 쓰지 않는다.
  폴더를 옮기면 URL 이 어긋나므로 다시 만든다.
- `repo-01`: 작업 저장소. main 한 줄기 커밋 N+1개(파일 `VERSION` 하나)는 두 저장소가 같다. `origin/main` 이 main 과 같고 upstream 이
  잡혀 있다. commit-graph 있음.
- tag i(0부터)의 이름은 `v<i/1000>.<i/100 % 10>.<i % 100>`(5만이면 `v0.0.0` … `v49.9.99`, `/` 없는 평평한 이름)이고 i+1 번째 커밋을
  가리킨다. `i % 3` 이 2 면 경량, 아니면 annotated 다(약 2/3).
- 두 저장소의 ref 는 `pack-refs --all` 로 묶는다(clone·gc 뒤의 모양). 같은 tag 는 annotated 객체 oid 까지 같다.
- 원격 상태는 `i % 20` 으로 정한다. 비교 기준은 계획 TG-08 처럼 ref 가 가리키는 객체 oid 다.

| `i % 20` | 상태                           | 로컬          | 원격                                     | 비율 |
| -------- | ------------------------------ | ------------- | ---------------------------------------- | ---- |
| 0·1      | 로컬에만 (`localOnly`)         | 있음          | 없음                                     | 10%  |
| 2·3      | 원격에만 (`remoteOnly`)        | 없음          | 있음                                     | 10%  |
| 4        | 다름, 다른 커밋                | i+1 번째 커밋 | 그 다음 커밋, 같은 종류                  | 5%   |
| 5        | 다름, 같은 커밋 (`sameCommit`) | i+1 번째 커밋 | 같은 커밋, 종류가 반대(annotated ↔ 경량) | 5%   |
| 그 밖    | 같음 (`same`)                  | 같은 객체     | 같은 객체                                | 70%  |

"같음"이 아닌 항목(IPC 보고서에 실리는 것)은 N 의 30% 다. 끝에 찍는 개수는 앱과 같은 `ls-remote --tags origin`(`^{}` 줄 포함)과
로컬 `for-each-ref` 를 객체 oid 로 견준 값이다.

### 실행

```bash
cargo run --release -p mgit-bench -- --tags bench/repos/tags-10000 --runs 5
cargo run --release -p mgit-bench -- --tags bench/repos/tags-50000 --runs 5 --write-runs 0                  # 읽기만
cargo run --release -p mgit-bench -- --tags bench/repos/tags-50000 --runs 1 --write-runs 1 --one-chunk-runs 0 --write-limit 1000  # 1천 개만 한 번
```

옵션: `--runs N`(읽기 반복, 기본 3), `--write-runs N`(일괄 push·삭제 반복, 기본 `--runs`, 0 이면 건너뜀),
`--one-chunk-runs N`(청크 예산 없는 비교, 기본 `--write-runs`, 0 이면 건너뜀), `--write-limit N`(이보다 큰 일괄 묶음은 재지 않음).
쓰기는 큰 픽스처에서 한 번에 수 분이 걸린다(아래 "일괄 push·원격 삭제").

| 출력                                          | 재는 것                                                                                                                                    |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `refresh_ms` (`refresh_ls_remote_ms`)         | `Core::remote_tags(origin, refresh=true)` 한 번 — 전체 `ls-remote --tags` + 파싱 + 비교 + 보고서. 괄호는 명령 로그의 ls-remote 몫(ms 단위) |
| `direct_ls_remote_ms`·`parse_ms`·`compare_ms` | 같은 ls-remote 를 벤치가 직접 돌린 시간, 그 출력의 `parse_ls_remote_tags`, 지금 라벨과의 `compare_tags` (코어 안의 몫을 바깥에서 재현)     |
| `cached_ms`                                   | `remote_tags(refresh=false)` — 네트워크 없이 캐시 + 로컬 라벨로 보고서 (IPC 응답을 만드는 비용)                                            |
| `report_json_ms`·`report_json_bytes`          | `serde_json::to_vec(&보고서)` — IPC 직렬화. 합격선 2MB(10진)·캐시 보고서와 합쳐 100ms                                                      |
| `refs_json_ms`·`refs_json_bytes`              | `RefsChanged` 가 싣는 `RepoRefs`(라벨 전부) JSON — 지금 동작의 기준선(코어 serde, 셸 DTO 와 필드가 같다)                                   |
| `lookup_1_ms`·`lookup_50_ms`·`lookup_51_ms`   | `lookup_remote_tags` 이름 1·50개(이름별 패턴)·51개(전체 조회) — 원격 삭제 직전 조회와 같은 경로                                            |
| `push_ms`·`push_git`                          | 로컬에만 있는 tag k개의 `push_tags`(op 붙임)와 그 git push 수(청크 수)                                                                     |
| `delete_ms`·`delete_lookup_ms`·`delete_git`   | 같은 tag 의 `delete_remote_tags`, 그 안의 직전 조회(ls-remote) 몫, git push 수                                                             |
- 읽기는 픽스처를 그대로 연다(원격을 바꾸지 않는다). 쓰기는 `repo-01`·`origin.git` 을 `<픽스처>/.bench-tmp/` 에 복사하고 복사본의
  origin URL 을 복사한 원격으로 바꿔서 한다. 실행마다 push → 삭제 짝이라 복사본은 처음 상태로 돌아오고, 끝나면(실패해도) 복사본을
  지운다. 중간에 죽어 남은 복사본은 다음 실행이 먼저 지운다.
- k 는 로컬에만 있는 tag 전부이고(1천 → 100, 1만 → 1,000, 5만 → 5,000), 1천 개를 넘으면 1천 개도 따로 잰다. 가장 큰 k 는 청크 예산을
  없앤 코어(`tag_chunk_bytes`·`tag_chunk_refs` = 최대, 명령 하나)로도 재서 청크 비용을 견준다.
- 벤치의 비교 결과 개수가 코어 보고서와 다르면 실패로 멈춘다. push 가 모두 `pushed`, 삭제가 모두 `deleted` 가 아니어도 멈춘다.

읽는 법과 한계:

- 보고서 항목 하나가 약 234 B(oid hex 4개 + 이름 + 상태)다. 2MB 에는 약 8,500개가 들고, 이 픽스처 비율(30%)로는 tag 약 2.8만 개가 경계다.
- 전체 조회의 대부분은 ls-remote 다. 파싱·비교는 5만에서도 18ms 다. 부하가 낮을 때(load 9) 5만을 한 번 더 재면 전체 조회 86ms
  (ls-remote 64), IPC 15ms 였다.
- 일괄 push·삭제가 느린 원인은 git 클라이언트다. 5만 push 중 `sample <pid>` 로 스택을 뜨면 `check_push_refs → match_explicit_lhs →
  count_refspec_match → refname_match → mkpath`(snprintf)가 CPU 를 다 쓰고 receive-pack 은 놀았다. 비용이 대략 refspec 수 × ref 수다
  — 같은 1천 개가 라벨 5배(9,002 → 45,002)에서 push 4.4배·삭제 4.7배 느려졌다. 5만의 5천 개는 이 법칙으로 1천 개 값의 5배를 어림한
  **추정값**이다(한 번에 수 분이라 재지 않았다).
- 청크로 나눠도 합계는 같다(1만: 8.0s ↔ 예산 없음 7.7s). 청크 예산은 명령 줄 길이만 지킨다.
- 이름별 패턴 50개가 전체 조회보다 3~4배 느리다. 패턴 하나는 전체 조회와 비슷하다.
- 원격은 같은 기기의 bare 저장소다. 실제 네트워크·서버(GitHub 등)의 왕복과 ref 광고 시간은 들어 있지 않다. 트리 3,000 개 렌더링
  (`frontend-measure.js`)은 재지 않았다(U 레인 화면 작업 뒤 따로).

판단 (H1.5, 팀장):

- 보고서 2MB 초과: 지연 조회 슬라이스를 넣지 않는다. 크기 기준은 전송 비용의 대리 지표이고 IPC 시간(24ms)은 기준 안이며, 같은
  규모에서 `RefsChanged` 가 이미 11MB 를 보낸다. "같음"이 아닌 것이 30% 인 5만 개는 극단적인 경우다. 후속 후보: 항목에서 로컬 oid
  두 개 빼기(약 35% 감소, 어림), entries 를 따로 조회하기.
- `RefsChanged` 기준선: 지금 동작이고 범위 밖이다. 후속 항목으로 기록만 한다.
- 일괄 push·삭제의 git 클라이언트 비용: 알려진 한계로 둔다. 후속 아이디어(아이디어만): 고른 것이 그 원격의 "로컬에만" 전부일 때
  패턴 refspec 쓰기 등.
- 단일 조회: 이름별 패턴은 4개 이하일 때만 쓰도록 R 의 C2c 에서 바꾼다.
