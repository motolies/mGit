# 패키징

mGit을 로컬에서 `.app`·`.dmg`로 만들고 서명·검증하는 방법입니다. 릴리스는 macOS Apple Silicon용으로 만들며 GitHub push·게시·자동 업데이트는 수행하지 않습니다. 받은 dmg를 설치하는 사람은 4·5절을 보면 됩니다.

기준: 2026-11-25 · 저장소의 `package.json`, `scripts/release.mjs`, `scripts/signing-identity.swift`, `apps/desktop/src-tauri/tauri.conf.json`. 아래는 실행 절차와 검증 조건이며 모든 명령을 실행했다는 기록은 아닙니다.

## 0. 한눈에

개발용 실행·일반 빌드는 기존 명령을 그대로 사용합니다.

```bash
pnpm dev
pnpm build
```

버전을 고정한 로컬 릴리스는 별도 명령을 사용합니다. 최초에는 1절의 서명 키를 준비하고, 7절대로 버전과 공개 인증서 정보를 commit합니다. 릴리스 명령은 깨끗한 작업 트리와 현재 commit을 가리키는 정확한 버전 태그를 요구합니다.

```bash
pnpm release:tag
pnpm release:check
pnpm release:macos
```

`0.1.0`의 결과는 다음 디렉터리에 모입니다.

| 결과물      | 경로                                    | 용도                                                       |
| ----------- | --------------------------------------- | ---------------------------------------------------------- |
| 앱 번들     | `release/v0.1.0/mGit.app`               | 코드 서명이 적용된 Apple Silicon 앱입니다.                 |
| 설치 이미지 | `release/v0.1.0/mGit_0.1.0_aarch64.dmg` | 다른 Mac으로 옮길 설치 파일입니다.                         |
| 체크섬      | `release/v0.1.0/SHA256SUMS`             | 결과 파일의 SHA-256을 확인합니다.                          |
| 릴리스 기록 | `release/v0.1.0/manifest.json`          | 버전·Git commit·태그·서명 인증서·산출물 정보를 확인합니다. |

`pnpm build`의 출력은 기존 `target/release/bundle/`입니다. `release:macos`의 검증·수집을 통과한 파일은 `release/v<버전>/`에서 확인합니다. 둘을 혼동하지 않습니다.

## 1. 처음 한 번

준비물과 의존성 설치는 [빌드·테스트 1·2절](빌드-테스트.md#1-준비물)을 따릅니다. 릴리스 도구는 macOS의 `codesign`, `security`, `hdiutil`, Swift 도구와 OpenSSL을 사용합니다. 로컬 릴리스 대상은 Apple Silicon이며 Intel·universal 빌드는 3절의 수동 경로로 구분합니다.

### 로컬 서명 키 준비

```bash
pnpm signing:setup
pnpm signing:status
```

`signing:setup`은 CN이 `mGit`인 RSA 3072비트 자체 서명 인증서와 개인키를 준비합니다. 인증서의 유효기간은 36,500일(약 100년)로 설정합니다. 처음 만든 인증서와 개인키를 키체인에 가져오고 복구용 백업을 자동으로 만듭니다. 기본 키체인은 로그인 키체인입니다.

이미 공개 인증서 정보가 있거나 같은 이름의 다른 인증서가 있으면 새 키로 조용히 바꾸지 않습니다. 기존 키를 복원할 때는 아래의 `signing:import`를 사용합니다.

| 위치                                                                  | 내용                                                       | 관리                                           |
| --------------------------------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------- |
| `packaging/signing-identity.json`                                     | CN·SHA-1·SHA-256·만료 시각 등 공개 인증서 식별 정보입니다. | 검토 후 Git에 commit합니다. 개인키는 없습니다. |
| `signing/mGit-<지문 앞 12자리>-<UTC 시각>-<임의 접미사>/identity.p12` | 인증서와 개인키를 담은 암호화된 백업입니다.                | Git에 넣지 않습니다.                           |
| 같은 폴더의 `password.txt`                                            | PKCS#12 백업 암호입니다.                                   | 개인키와 같은 수준으로 보호합니다.             |
| 같은 폴더의 `certificate.cer`                                         | 인증서 사본입니다.                                         | 백업 묶음과 함께 보관합니다.                   |
| 같은 폴더의 `identity.json`                                           | 해당 백업의 인증서 식별 정보입니다.                        | 복원할 백업을 구분할 때 사용합니다.            |

`packaging/signing-identity.json`을 검토해 commit한 뒤 버전 준비를 진행합니다. `release:prepare`는 작업 트리가 깨끗해야 실행됩니다.

`signing/`은 Git 제외 대상입니다. 백업 폴더 권한은 `0700`, 파일은 `0600`으로 제한합니다. 자동 생성한 백업을 장기 보관할 위치로 복사해 두어야 다른 Mac이나 키체인 초기화 뒤에도 같은 키를 복원할 수 있습니다. 백업과 암호를 함께 가진 사람은 같은 이름으로 앱을 서명할 수 있으므로 백업 묶음을 공유하거나 로그에 암호를 붙이지 않습니다.

### 백업·복원·상태 확인

```bash
pnpm signing:export
pnpm signing:status --json
```

`signing:export`는 공개 정보에 고정된 인증서와 개인키만 새 백업 묶음으로 내보냅니다. 키체인 전체를 내보내지 않습니다. 명령이 출력한 백업 디렉터리를 보관합니다.

복원할 때는 실제 백업 디렉터리를 `--bundle`에 지정합니다. 아래 `BACKUP_DIR`은 사용자가 보관한 경로로 바꿉니다.

```bash
BACKUP_DIR='./signing/복원할-백업-디렉터리'
pnpm signing:import --bundle "$BACKUP_DIR"
pnpm signing:status
pnpm signing:verify-backup --bundle "$BACKUP_DIR"
```

`signing:verify-backup`은 백업을 별도 임시 키체인에 복원하고 시험 실행 파일의 서명과 인증서 지문을 검증한 뒤 정리합니다. 로그인 키체인의 기존 identity와 원본 백업은 변경하지 않습니다.

`--keychain <경로>`로 별도 키체인을 점검하거나 가져오기를 수행할 수 있습니다. 릴리스 명령은 기본 로그인 키체인의 상태를 검사하므로 실제 릴리스에 쓸 키는 그곳에 준비합니다. `setup`·`import`는 해당 인증서에 코드 서명용 사용자 신뢰를 설정하며 macOS의 키체인 접근·신뢰 확인 창이 나타날 수 있습니다. `status --json`은 암호 대신 공개 식별 정보·키체인·상태를 출력하며, 준비된 상태(`ready`)일 때만 종료 코드 0을 반환합니다. 공개 정보의 지문과 가져올 키가 다르면 가져오기를 중단하고 기존 키는 삭제하지 않습니다.

자체 서명은 Apple Developer ID나 Apple 공증이 아닙니다. 이 Mac에서 키가 준비됐다는 것과 다른 Mac에서 Gatekeeper가 앱을 허용한다는 것은 별개입니다(5·6절).

## 2. 만들기

개발 중 일반 `.app`·`.dmg` 빌드는 저장소 루트에서 `pnpm build`를 실행합니다. 이 명령은 기존 ad-hoc 서명 설정을 유지합니다. 고정된 서명 키와 Git 버전 검증을 사용하는 릴리스는 8절의 `pnpm release:macos`로 만듭니다.

> [!WARNING]
> 셸에 `VITE_MGIT_MOCK` 이 남은 채 빌드하면 목 앱이 만들어집니다. 목 앱은 실제 저장소 대신 합성 데이터를 보여 주고, 그 안에서 한 작업은 저장소에 반영되지 않습니다. 빌드 전에 `echo "$VITE_MGIT_MOCK"` 가 빈 줄인지 보고, 값이 있으면 `unset VITE_MGIT_MOCK VITE_MGIT_MOCK_SCENE` 으로 지웁니다. → [빌드·테스트 4절](빌드-테스트.md#4-목-모드--코어-없이-화면만-보기)
1. 목 변수가 비어 있는지 확인합니다(위 WARNING).
2. 빌드합니다.

   ```bash
   pnpm build
   ```

3. 터미널 끝에 `Finished 2 bundles at:` 과 결과물 경로 두 줄이 나오면 끝입니다.

`pnpm build` 는 화면을 빌드하고(`beforeBuildCommand` → `apps/desktop/dist`), Rust 를 release 로 컴파일한 뒤, `.app` 을 만들어 서명하고 `.dmg` 로 묶습니다. 출력의 주요 줄은 다음과 같습니다(경로는 줄임).

```text
     Running beforeBuildCommand `pnpm build:web`
    Finished `release` profile [optimized + debuginfo] target(s) in 1m 05s
    Bundling mGit.app (…/target/release/bundle/macos/mGit.app)
     Signing with identity "-"
        Warn skipping app notarization, no APPLE_ID & APPLE_PASSWORD & APPLE_TEAM_ID or APPLE_API_KEY & APPLE_API_ISSUER & APPLE_API_KEY_PATH environment variables found
    Bundling mGit_0.1.0_aarch64.dmg (…/target/release/bundle/dmg/mGit_0.1.0_aarch64.dmg)
    Finished 2 bundles at:
        …/target/release/bundle/macos/mGit.app (46.88 MiB)
        …/target/release/bundle/dmg/mGit_0.1.0_aarch64.dmg (12.80 MiB)
```

- 화면 빌드 중에 `(!) Some chunks are larger than 500 kB after minification` 경고가 나옵니다. 큰 화면 코드 묶음이 있다는 안내이고 빌드는 계속됩니다.
- `Signing with identity "-"` 는 임시(ad-hoc) 서명입니다(5절).
- `Warn skipping app notarization …` 은 Apple 공증에 쓸 값이 없어 공증을 건너뛴다는 뜻입니다. Apple 공증 자격 정보를 사용하지 않는 빌드에서 나옵니다(6절).
- 같은 버전이면 이전 결과물을 덮어씁니다. `bundle/dmg/` 의 `bundle_dmg.sh`·`icon.icns` 는 dmg 를 만들 때 쓴 파일입니다.

빌드 시간과 파일 크기는 현재 소스·캐시·환경에 따라 달라집니다. 위 출력은 이전 일반 빌드의 예시이며 이번 릴리스의 측정값이 아닙니다.

### `.app` 이나 `.dmg` 하나만 만들기

하나만 필요하면 `--bundles` 로 고릅니다.

```bash
pnpm build --bundles app   # .app 만
pnpm build --bundles dmg   # .dmg 만
```

- `pnpm build` 뒤에 붙인 인자는 `tauri build` 에 그대로 갑니다. `--` 는 필요 없습니다. 출력 첫 줄들에 `$ tauri build --bundles app` 처럼 보이면 전달된 것입니다.
- `--bundles app` 은 `.dmg` 를 건드리지 않습니다. 폴더에 있던 dmg 는 예전 것 그대로 남습니다.
- `--bundles dmg` 도 안에서 `.app` 을 먼저 만들지만, dmg 를 만든 뒤 그 `.app` 을 지웁니다(출력에 `Cleaning …/mGit.app`). `bundle/macos/` 에는 남는 것이 없습니다.
- macOS 에서 고를 수 있는 값은 `app`·`dmg`(와 `ios`)입니다. 다른 옵션은 `apps/desktop` 폴더에서 `./node_modules/.bin/tauri build --help` 로 봅니다.

## 3. Apple Silicon·Intel 둘 다 도는 앱 (universal)

Intel Mac 에서도 돌게 하려면 universal 로 만듭니다. 2절의 결과물은 Apple Silicon 에서만 돕니다.

> [!NOTE]
> 이 절은 실제로 만들어 보지 않았습니다(확인 전). 명령은 tauri-cli 2.12.4 의 `tauri build --help` 와 Tauri 문서를 따른 것입니다.
1. Intel용 Rust 타깃이 없으면 `rustup target add x86_64-apple-darwin`으로 추가합니다.
2. universal 로 빌드합니다.

   ```bash
   pnpm build --target universal-apple-darwin
   ```

3. 결과물은 `target/universal-apple-darwin/release/bundle/` 아래에 생깁니다.

| 결과물 | 경로                                                                        |
| ------ | --------------------------------------------------------------------------- |
| `.app` | `target/universal-apple-darwin/release/bundle/macos/mGit.app`               |
| `.dmg` | `target/universal-apple-darwin/release/bundle/dmg/mGit_0.1.0_universal.dmg` |
- Apple Silicon 용과 Intel 용을 따로 컴파일해 하나로 합치므로 2절보다 오래 걸리고 파일도 큽니다(재지 않음).
- 실행 파일에 든 아키텍처는 `lipo -archs <앱>/Contents/MacOS/mgit-desktop` 으로 봅니다. 2절의 결과물은 `arm64` 하나이고, universal 이면 `x86_64` 와 `arm64` 가 함께 보여야 합니다.
- 최소 macOS 는 둘 다 15.0 입니다(`tauri.conf.json` 의 `minimumSystemVersion`).

## 4. 설치하기

받은 `.dmg` 로 설치하려면 다음과 같이 합니다. [사용법 1.2](사용법/1-설치와-첫-실행.md#12-앱-설치하기)와 같은 절차를 조금 더 자세히 적었습니다.

1. `.dmg` 파일을 더블클릭합니다. mGit 아이콘과 `Applications` 폴더 바로가기가 든 창이 열립니다.
2. mGit 아이콘을 `Applications` 바로가기 위로 끌어 놓습니다. 응용 프로그램 폴더로 복사됩니다.
3. 창을 닫고, Finder 사이드바의 위치 목록에서 dmg 디스크 옆 꺼내기 단추(⏏)를 눌러 꺼냅니다. dmg 파일은 지워도 됩니다.
4. 응용 프로그램 폴더에서 mGit 을 엽니다. 다른 Mac 에서 만든 dmg 라서 경고가 뜨면 5절을 따릅니다.

받을 Mac 이 Intel 이면 `aarch64` dmg 로는 열리지 않습니다. universal dmg(3절)를 받습니다. Apple 메뉴 > 이 Mac에 관하여 에서 칩이 Apple M 으로 시작하면 Apple Silicon, 프로세서가 Intel 이면 Intel 입니다.

### 이미 설치돼 있으면

새 버전으로 바꾸려면 열려 있는 mGit 을 `⌘Q` 로 끝낸 뒤 위 1~3을 똑같이 합니다. Finder 가 같은 이름의 항목이 있다고 물으면 기존 것을 대치하는 쪽을 고릅니다(macOS 표기는 버전마다 다를 수 있음).

- 최근 목록·열린 탭·설정은 앱 파일 밖(데이터 폴더 `~/Library/Application Support/io.github.motolies.mgit/` 등)에 저장되므로 앱을 바꿔도 남습니다. 호스팅 계정 토큰은 키체인에 있습니다. 저장되는 곳은 [사용법 8장](사용법/8-설정.md) 머리의 표에 있습니다.
- 소스에서 `pnpm dev` 로 띄운 앱도 이 데이터 폴더를 함께 씁니다([빌드·테스트 3절](빌드-테스트.md#3-개발-실행)).
- 앱을 지우려면 응용 프로그램 폴더의 mGit 을 휴지통으로 옮깁니다. 데이터 폴더는 남습니다. 버린 파일의 백업 사본([사용법 6.3](사용법/6-실수했을-때.md#63-버린-파일-되살리기))도 이 폴더의 `backups` 에 있으니, 데이터 폴더까지 지울 때는 필요한 것이 없는지 먼저 봅니다.

## 5. 다른 Mac 에서 열기

받은 dmg 로 설치한 mGit 이 경고와 함께 열리지 않으면 이 절을 따릅니다.

### 왜 경고가 뜨나

- `pnpm build`는 기존 임시(ad-hoc) 서명 설정(`tauri.conf.json`의 `"signingIdentity": "-"`)을 사용합니다. `pnpm release:macos`는 공개 지문으로 고정한 `mGit` 자체 서명 인증서를 사용합니다. 두 경로 모두 Apple Developer ID 서명·Apple 공증과는 다릅니다(6절).
- 브라우저 등으로 내려받은 파일에는 macOS 가 격리 속성(`com.apple.quarantine`)을 붙입니다. 격리 속성이 있는 앱을 처음 열면 Gatekeeper 가 서명과 공증을 검사하고, 정식 서명이 아니어서 막습니다.
- 경고 문구는 macOS 버전마다 다릅니다. Apple 이 악성 소프트웨어가 있는지 확인할 수 없다는 경고나, 확인되지 않은 개발자라는 경고가 흔합니다. 경고 창에서는 완료를 눌러 닫습니다(휴지통으로 옮기지 않습니다).
- 직접 빌드한 Mac 의 결과물에는 격리 속성이 붙지 않습니다(`xattr -l` 로 확인).

### 방법 1. 시스템 설정의 "그래도 열기"

macOS 15 부터는 Finder 에서 Control-클릭(우클릭) → 열기로 이 검사를 넘길 수 없습니다([Apple 개발자 소식, 2024-08-06](https://developer.apple.com/news/?id=saqachfa)). 시스템 설정에서 허용합니다.

1. 응용 프로그램 폴더에서 mGit 을 한 번 열어 봅니다. 경고가 뜨면 완료를 누릅니다.
2. Apple 메뉴 > 시스템 설정을 고르고, 사이드바에서 개인정보 보호 및 보안을 누릅니다. 아래로 스크롤해야 할 수 있습니다.
3. 보안 항목으로 내려가 mGit 이 차단됐다는 안내 옆의 단추(열기 또는 "그래도 열기")를 누릅니다.
4. 확인 창이 뜨면 "그래도 열기"를 누릅니다. 이 단추는 앱을 열려고 한 때부터 약 1시간 동안만 쓸 수 있습니다. 시간이 지났으면 1부터 다시 합니다.
5. 로그인 암호를 입력하고 확인을 누릅니다.

단계와 단추 이름은 Apple 지원 문서 [알 수 없는 개발자의 Mac 앱 열기](https://support.apple.com/ko-kr/guide/mac-help/mh40616/mac)(영문 "Open Anyway")를 따랐습니다. macOS 표기는 버전마다 다를 수 있고, 이 문서를 쓸 때 실제 경고 창은 띄워 보지 않았습니다.

### 방법 2. 터미널에서 격리 속성 지우기

터미널을 쓸 줄 알면 격리 속성을 지워도 됩니다.

```bash
xattr -dr com.apple.quarantine /Applications/mGit.app
```

- `-d` 는 속성 지우기, `-r` 은 앱 안의 모든 파일까지라는 뜻입니다. 지운 앱은 내려받지 않은 앱처럼 취급되어 Gatekeeper 가 막지 않습니다.
- 위험: 이 앱에 대해 macOS 의 검사를 건너뛰는 것입니다. 직접 만들었거나 믿을 수 있는 사람에게 받은 파일에만 씁니다.
- 서명은 그대로입니다. 격리 속성을 붙인 복사본으로 시험했을 때 이 명령 뒤 격리 속성이 모두 사라졌고 `codesign --verify` 도 그대로 통과했습니다.

### 서명 상태 확인하기

앱의 서명과 격리 상태는 아래 명령으로 봅니다. 서명 자체의 유효성과 Apple의 배포 허용 판정은 서로 다른 검사입니다.

| 명령                                                       | 이 앱에서 나오는 것                                                  | 뜻                                                      |
| ---------------------------------------------------------- | -------------------------------------------------------------------- | ------------------------------------------------------- |
| `codesign -dv --verbose=2 /Applications/mGit.app`          | 일반 빌드는 `Signature=adhoc`, 자체 서명 릴리스는 인증서 정보입니다. | 어떤 서명 방식인지 확인합니다.                          |
| `codesign --verify --deep --strict /Applications/mGit.app` | 출력 없음(종료 코드 0)                                               | 서명이 깨지지 않음                                      |
| `spctl -a -vv /Applications/mGit.app`                      | `/Applications/mGit.app: rejected`                                   | Gatekeeper 가 승인하지 않음. 격리 속성이 있든 없든 같음 |
| `xattr -l /Applications/mGit.app`                          | `com.apple.quarantine: 0081;…` 줄                                    | 격리 상태. 방법 2 뒤에는 이 줄이 없어짐                 |

일반 `pnpm build`로 만든 ad-hoc 앱의 출력 예시입니다. 자체 서명 릴리스에서 `Signature=adhoc`가 나오면 의도한 인증서로 서명되지 않은 것입니다.

```text
Identifier=io.github.motolies.mgit
Format=app bundle with Mach-O thin (arm64)
CodeDirectory v=20500 size=95889 flags=0x10002(adhoc,runtime) hashes=2990+3 location=embedded
Signature=adhoc
TeamIdentifier=not set
```

- `thin (arm64)` 는 Apple Silicon 전용이라는 뜻입니다.
- 일반 빌드와 로컬 릴리스의 서명 검증 대상은 앱 번들입니다. DMG의 무결성은 릴리스 도구의 이미지 검사와 `SHA256SUMS`로 확인합니다.

### 받은 Mac 의 git

mGit 은 git 을 품고 있지 않고 그 Mac 에 설치된 git 을 씁니다. Finder 로 켠 mGit 은 보통 Command Line Tools 의 git(`/usr/bin/git`)을 쓰므로, 받은 Mac 의 터미널에서 `/usr/bin/git --version` 이 2.45 이상이어야 합니다. 없거나 낮으면 앱 상태 바 오른쪽 끝에 **git 없음** 이 보입니다. Homebrew 로 새 git 을 설치해도 Finder 로 켠 앱은 그 git 을 쓰지 않을 수 있으니(확인 전), Command Line Tools 를 설치하거나 올립니다. 자세한 것은 [사용법 1.1](사용법/1-설치와-첫-실행.md#11-요구-사항)과 [10.1](사용법/10-문제-해결.md#101-git-이-없거나-버전이-낮을-때)에 있습니다.

## 6. 정식 서명·공증 (다루지 않음)

경고 없이 열리는 앱을 나눠 주려면 Apple 정식 서명과 공증이 필요합니다. 유료 Apple Developer Program 계정과 그 계정 소유자(Account Holder)가 만든 Developer ID Application 인증서가 있어야 하고, 빌드할 때 환경 변수로 넘깁니다. 서명은 `APPLE_SIGNING_IDENTITY`(또는 `tauri.conf.json` 의 `signingIdentity` 를 바꿈), CI 에서 인증서를 넘길 때는 `APPLE_CERTIFICATE`·`APPLE_CERTIFICATE_PASSWORD`, 공증은 `APPLE_ID`·`APPLE_PASSWORD`·`APPLE_TEAM_ID` 또는 `APPLE_API_KEY`·`APPLE_API_ISSUER`·`APPLE_API_KEY_PATH` 입니다. 공증 값이 없으면 2절의 `Warn skipping app notarization` 처럼 공증을 건너뜁니다. 절차는 Tauri 문서 [macOS Code Signing](https://v2.tauri.app/distribute/sign/macos/)과 그 안의 [Notarization](https://v2.tauri.app/distribute/sign/macos/#notarization) 절에 있습니다. 이 저장소에서는 정식 서명·공증을 해 보지 않았습니다(검증하지 않음).

## 7. 버전 올리기

새 버전은 저장소 루트에서 준비합니다. 서명 설정과 다른 소스 변경을 먼저 commit해 작업 트리를 깨끗하게 만듭니다. 아래는 `0.1.1`을 준비하는 예시입니다.

```bash
pnpm release:prepare 0.1.1
```

이 명령은 앱·Rust workspace·JavaScript workspace의 버전을 같은 값으로 맞추고 Cargo 잠금 파일을 갱신합니다. 수동으로 일부 파일만 바꾸지 않습니다. 변경 목록을 검토한 뒤 버전 변경과 필요한 공개 인증서 정보를 commit합니다. 이 단계는 commit이나 tag를 대신 만들지 않습니다.

- Tauri 앱 버전: `apps/desktop/src-tauri/tauri.conf.json`입니다.
- Rust 버전: 루트 `Cargo.toml`, 별도로 버전을 선언하는 crate, `Cargo.lock`의 로컬 crate 항목입니다.
- JavaScript 버전: 루트·desktop·`packages/`의 workspace `package.json`입니다.
- `pnpm-lock.yaml`은 이 명령으로 변경하지 않습니다. 버전 준비는 외부 의존성을 업데이트하지 않습니다.

`release:prepare`는 로컬 파일을 변경하는 명령입니다. `release:check`는 결과를 검사하는 명령이며, 검사 실패를 고치려고 버전이나 Git 태그를 자동 변경하지 않습니다.

## 8. 로컬 릴리스 만들기

이 절은 **로컬 태그와 로컬 설치 파일**을 만드는 절차입니다. GitHub push, GitHub Releases 업로드·게시, updater 서명·설정은 포함하지 않습니다.

### 한 번에 실행하기

코드 변경을 먼저 commit한 뒤 아래 명령 하나로 실행할 수 있습니다.

```bash
pnpm release 0.1.1
# 또는 ./scripts/release.sh 0.1.1
```

서명 키·Git 상태를 먼저 확인한 뒤 버전 파일 갱신 → 버전 변경만 자동 commit → 로컬 태그 생성 → 사전 검사 → 앱·DMG 생성 순서로 실행합니다. 작업 중인 코드까지 자동으로 commit하지 않으며, 시작할 때 작업 트리가 깨끗해야 합니다.

`pnpm release 0.1.1 --dry-run`으로 실행할 단계를 미리 볼 수 있습니다. 버전을 생략한 `pnpm release`는 현재 버전을 사용합니다. 빌드에 실패하면 완료된 버전 commit과 태그를 보존하며, 같은 명령으로 재시도하면 올바른 기존 태그를 재사용합니다. 다른 commit의 태그를 이동하거나 기존 배포 결과를 덮어쓰지 않고 원격 push도 하지 않습니다.

### 단계별 실행: 준비와 태그

1. 1절의 서명 키가 `ready`인지 확인합니다.
2. 7절로 버전을 맞추고 변경을 검토해 commit합니다. Git에 포함할 것은 코드·설정·공개 인증서 정보이며 `signing/` 백업과 `release/` 결과물은 제외합니다.
3. 현재 commit에 버전 태그를 만듭니다.

   ```bash
   pnpm release:tag
   ```

`release:tag`는 현재 버전이 `0.1.0`이면 로컬 annotated tag `v0.1.0`을 만듭니다. 태그를 원격으로 push하지 않습니다. 기존 태그를 다른 commit으로 강제 이동하지 않습니다. 이미 태그가 있으면 생성은 실패하므로, 올바른 태그가 준비된 상태에서는 `release:check`부터 실행합니다.

### 사전 검사와 패키징

```bash
pnpm release:check
pnpm release:macos
```

검사는 manifest의 버전 일치, 깨끗한 Git 작업 트리, 현재 HEAD를 가리키는 정확한 버전 annotated tag, 서명 키와 공개 지문 일치를 요구합니다. 환경의 `VITE_MGIT_MOCK`·`VITE_MGIT_MOCK_SCENE` 값이 비어 있지 않으면 중단합니다. 저장소 루트와 `apps/desktop`의 실제 `.env*` 파일에 이 변수의 할당이 있어도 중단하며 `.example`·`.sample` 파일은 제외합니다. 서명 키가 없거나 다른 키이면 ad-hoc 서명으로 대신 진행하지 않습니다.

`release:macos`는 Apple Silicon 앱과 DMG를 만들고 버전·아키텍처·서명·DMG를 검사한 뒤 `release/v<버전>/`에 산출물과 기록을 모읍니다. 일반 Tauri 설정을 영구 변경하지 않고 릴리스에 필요한 서명 설정을 적용하므로 `pnpm dev`와 `pnpm build`는 그대로 사용할 수 있습니다.

`prepare`·`check`·`tag`·`macos` 모두 `--dry-run`을 지원합니다. `prepare --dry-run`은 작업 트리가 수정된 상태에서도 변경 대상 파일을 보여 주며 파일을 쓰지 않습니다. 나머지 명령의 dry-run도 깨끗한 작업 트리 등 해당 사전 조건을 확인하고, `macos --dry-run`은 준비된 태그·서명 키와 출력 경로를 확인합니다. 실제 빌드·서명·설치 검증을 대신하지 않습니다.

```bash
pnpm release:macos --dry-run
```

같은 `release/v<버전>/` 디렉터리가 이미 있으면 덮어쓰지 않고 중단합니다. 빌드 중간 파일은 `target/release-macos/`를 사용하며, 최종 폴더는 앱과 DMG 검증을 모두 마친 뒤 게시합니다. 빌드 도중 소스나 태그가 바뀌어도 결과 게시를 중단합니다.

### 결과 확인

`release/v0.1.0/`을 예로 들면 다음과 같이 확인합니다.

```bash
codesign --verify --deep --strict release/v0.1.0/mGit.app
lipo -archs release/v0.1.0/mGit.app/Contents/MacOS/mgit-desktop
plutil -p release/v0.1.0/mGit.app/Contents/Info.plist
hdiutil verify release/v0.1.0/mGit_0.1.0_aarch64.dmg
cd release/v0.1.0
shasum -a 256 -c SHA256SUMS
```

`SHA256SUMS`에는 DMG, `manifest.json`, 앱 안의 실행 파일(`Contents/MacOS/mgit-desktop`) 해시가 있습니다. 앱 디렉터리 전체를 하나의 해시로 계산한 것은 아니며, 앱 자원은 `codesign --verify --deep --strict`로 검증합니다. 릴리스 도구는 DMG를 읽기 전용으로 붙여 그 안의 앱 서명과 실행 파일도 검사한 뒤 해제합니다.

아키텍처는 `arm64`, 앱 버전은 태그의 버전과 일치해야 합니다. `manifest.json`에서 해당 결과를 만든 commit과 인증서 지문을 확인합니다. `codesign` 성공은 파일 서명이 유효하다는 뜻이며, 다른 Mac의 Gatekeeper 승인이나 Apple 공증을 받았다는 뜻은 아닙니다.

## 9. Windows

Windows 판은 지금 만들지 않습니다. 이 Mac 에서는 만들 수 없고 CI 도 없습니다. 필요해지면 Windows 에서 직접 빌드하거나 GitHub Actions 를 다시 붙여 확인합니다. Windows 에서의 사용법은 이 문서들에서 다루지 않습니다.

- CI 를 지우기 전에 Windows 에서 컴파일과 clippy 는 통과했습니다. 테스트는 끝까지 돌려 보지 못했습니다(확인 전).
- 지금 `tauri.conf.json` 의 `bundle.targets` 는 `["app", "dmg"]` 로 macOS 형식만 적혀 있습니다. Windows 설치 파일(`msi`·`nsis`)을 만들려면 이 값도 바꿔야 할 수 있습니다(확인 전).

## 10. 문제 해결

### 서명 키 준비 또는 복원이 중단됨

`pnpm signing:status --json`의 상태와 `packaging/signing-identity.json`을 확인합니다. 비밀 파일의 내용을 출력할 필요는 없습니다.

| 상태        | 확인할 내용                                                                                                       |
| ----------- | ----------------------------------------------------------------------------------------------------------------- |
| `missing`   | 공개 정보나 키체인의 identity가 없습니다. 처음이라면 setup, 기존 키가 있다면 백업 import를 사용합니다.            |
| `mismatch`  | 공개 지문과 키체인 인증서가 다릅니다. 공개 정보를 임의 수정하거나 기존 키를 삭제하지 말고 올바른 백업을 찾습니다. |
| `ambiguous` | 같은 CN의 서로 다른 identity가 있습니다. 도구는 임의로 하나를 선택하지 않습니다.                                  |
| `untrusted` | 키는 있지만 코드 서명 신뢰가 준비되지 않았습니다. 같은 백업의 import로 신뢰 설정을 다시 진행합니다.               |
| `expired`   | 인증서가 만료되었습니다. 현재 도구는 다른 키로 자동 교체하지 않습니다.                                            |

setup 도중 키체인 접근이나 신뢰 설정이 중단돼도 백업과 최초 지문을 보존합니다. 출력된 백업 디렉터리로 `signing:import --bundle <경로>`를 실행해 이어갑니다. 개인키가 이미 있는데 다시 setup을 반복해 새 키를 만드는 흐름은 사용하지 않습니다.

### 릴리스 사전 검사 또는 재실행이 실패함

- 수정되거나 추적되지 않은 일반 파일이 있으면 중단합니다. 의도한 변경을 검토해 commit한 뒤 다시 검사합니다.
- 태그가 lightweight이거나 현재 commit·버전과 다르면 중단합니다. 태그를 자동으로 지우거나 강제 이동하지 않습니다.
- mock 환경 변수와 실제 `.env*`의 mock 할당을 확인합니다. `unset`만으로 `.env` 파일 내용까지 바뀌지는 않습니다.
- `release/v<버전>/`이 이미 있으면 결과를 덮어쓰지 않습니다. 새 릴리스 버전을 준비하거나 기존 결과의 보관 위치를 검토합니다.
- `release/.release.lock`이 있으면 다른 릴리스 실행이 진행 중인지 먼저 확인합니다. 실행 중인 작업의 잠금 파일을 지우지 않습니다.


### "확인되지 않은 개발자" 경고가 뜸

받은 Mac 에서 처음 열 때 뜨는 정상적인 경고입니다. Apple 이 악성 소프트웨어를 확인할 수 없다는 경고도 같습니다. [5절](#5-다른-mac-에서-열기)의 방법 1이나 2를 따릅니다.

### "손상되었기 때문에 열 수 없습니다" 류의 경고가 뜸

1. 서명이 깨졌는지 봅니다.

   ```bash
   codesign --verify --deep --strict /Applications/mGit.app
   ```

2. 아무것도 나오지 않고 끝나면(종료 코드 0) 서명은 멀쩡합니다. 격리 속성 때문이니 5절 방법 2로 지웁니다.
3. 오류가 나오면 옮기는 중에 파일이 바뀐 것입니다. dmg 를 다시 받아 설치합니다.

받은 Mac 이 Intel 인데 `aarch64` dmg 를 설치했어도 열리지 않습니다. universal dmg(3절)를 받습니다.

### 앱에 합성 데이터가 보임(목 모드가 들어간 앱)

상태 바의 git 버전에 `(mock)` 이 붙거나 탭 경로가 `/mock/…` 이면 목 모드로 빌드된 앱입니다. 빌드할 때 셸에 `VITE_MGIT_MOCK` 이 남아 있었던 것입니다.

1. `unset VITE_MGIT_MOCK VITE_MGIT_MOCK_SCENE` 으로 지웁니다.
2. `pnpm build` 로 다시 만들고 다시 설치합니다.
3. 그 dmg 를 이미 나눠 줬으면 새 dmg 로 바꿔 줍니다.

### 버전과 파일 이름이 맞지 않음

- dmg 이름과 앱 버전은 `tauri.conf.json` 의 `version` 에서 옵니다. `Cargo.toml`·`package.json` 만 바꾸면 이름은 그대로입니다. `pnpm release:prepare <버전>`으로 버전을 맞추고 commit한 뒤 검사합니다(7절).
- 로컬 릴리스는 태그와 `tauri.conf.json`의 버전이 다르면 사전 검사에서 중단합니다(8절).
- 폴더에 이전 버전 dmg 가 남아 있을 수 있습니다(7절 5).

### 빌드가 `beforeBuildCommand` 에서 실패함

``Running beforeBuildCommand `pnpm build:web` `` 다음에 오류로 끝나면 화면 빌드(vite)가 실패한 것이고 Rust 는 아직 시작하지 않았습니다. `pnpm check` 로 lint·typecheck·test 오류를 보고 고칩니다([빌드·테스트 5절](빌드-테스트.md#5-테스트와-검사)). 화면 빌드는 타입 검사를 하지 않으므로, 빌드가 됐더라도 나눠 주기 전에 `pnpm check` 를 돌립니다.

### 디스크 공간이 모자람

- release 빌드 결과는 `target/release/` 에 쌓입니다. 빈 `target/` 에서 한 번 빌드한 뒤 2.6GB 였습니다. 개발 실행·테스트가 쓰는 `target/debug/` 는 이보다 훨씬 큽니다([빌드·테스트 8절](빌드-테스트.md#8-문제-해결)).
- 자리가 모자라면 `cargo clean --release` 로 release 결과만 지웁니다. 만든 `.app`·`.dmg` 도 함께 지워지니 필요한 dmg 는 먼저 다른 곳에 옮깁니다. 다음 `pnpm build` 는 처음부터 컴파일합니다(2절 표의 1분 45초).
