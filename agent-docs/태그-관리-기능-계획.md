# mGit tag 관리 기능 계획

## Context

**왜 하는가**
- 사용자가 mGit 에서 tag 를 만든 뒤 원격으로 push 할 방법이 없다는 걸 확인했다.
  - Push 는 `refs/heads/*` 만 보낸다(`crates/mgit-core/src/sync.rs:174`).
  - 프런트는 `tags:false` 를 고정한다(`apps/desktop/src/store/session-store.ts:2573`).
- tag 삭제는 로컬 전용이다(`crates/mgit-core/src/branch.rs:338`).
- git 에는 원격 tag 추적 ref 가 없어서 원격 상태를 알 수 없다.
- 명세 BR-06 은 "삭제, 푸시 | P0" 인데 push 는 구현되지 않았다. 사용자 문서 3곳은 "기능 없음, 터미널을 쓰라"고 안내한다.

**목표**: 앱 안에서 tag 를 다 관리한다.
- push(하나·여럿·모든 tag)
- 로컬만·원격별·둘 다 삭제
- 원격 상태 확인(로컬에만 / 원격에만 / 같음 / 다름)
- 원격 tag 가져오기, 정리

사용자는 "MVP 를 넘어 깊게"를 요청했다.

**기획 과정**: `mt-plan` 이 `mt-ta`·`mt-ux` 검토를 거쳐 기획했고, 상위에서 핵심 코드 근거를 다시 확인했다.

**계획 검토 피드백 (2026-11-23)**
- 작업이 끝나면 사용설명서를 업데이트한다 → Phase M 을 추가했다.
- 병렬로 할 수 있는 단계는 병렬로 진행한다 → 레인 3개와 동기화 지점으로 재구성했다.

## 확정 결정

**사용자가 고른 것**
1. 지울 곳 대화상자의 기본 체크는 **로컬만**이다.
2. 원격 tag 가 로컬과 다른 commit 을 가리키면 **두 commit 을 보여 주고 확인한 뒤 삭제**한다. 여러 개면 "다른 tag 는 건너뛰고 삭제"도 고를 수 있다.
3. 범위에 **원격 상태 표시·가져오기, 모든 tag push, 일괄·정리**를 넣는다. 툴바 Push 의 follow-tags 는 넣지 않는다.
4. 서버 거부(`[remote rejected]`) 분류 수정은 **포함하되 별도 커밋**으로 한다.
5. 관리 화면은 **에디터 공간의 "태그" 문서 탭**이다. 로그를 보면서 관리하고, 폴더 탭 "개요" 표와 같은 방식이다.
6. 자동 fetch 에만 **`--no-prune-tags`** 를 붙인다. `fetch.pruneTags=true` 여도 백그라운드에서 tag 를 지우지 않는다. 수동 fetch 는 설정을 따른다.
7. 작업이 끝나면 **사용설명서를 종합 업데이트**한다(Phase M).
8. 병렬로 할 수 있는 단계는 **병렬로 진행**한다.

**권장안으로 정한 것**

| 항목                  | 결정                                                                                                                                                                         |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 강제 덮어쓰기         | `--force` 메뉴는 없다. "원격 것으로 맞추기"(로컬 교체, undo 가능)와 "로컬 것으로 맞추기"(lease 원격 삭제 후 push, danger 확인)로 한다. C5 이고 잘라도 된다                   |
| 제외                  | 이름 바꾸기, 폴더 탭, `push --tags`, `fetch --tags`, `--prune-tags`, `--atomic`                                                                                              |
| 후속                  | 서명 검증과 전체 메시지 보기, 문서가 보이는 동안 자동 재확인                                                                                                                 |
| 원격 상태 캐시        | `CoreInner` 에 canonical `common_dir` 키로, 원격별, 메모리에만 둔다(`write_locks` 와 같은 방식, `core.rs:106`). 명시적 "원격 확인" 때만 조회하고 자동 fetch 에 붙이지 않는다 |
| 원격 삭제             | 실행 직전에 `ls-remote` 로 조회하고 `--force-with-lease=refs/tags/<n>:<oid>` 로 삭제한다. 캐시는 표시용이고 lease 근거로 쓰지 않는다                                         |
| 원격 tag 와 다중 선택 | 원격에만 있는 tag 와 다중 선택은 브랜치 칸 트리에 넣지 않는다(문서 전용). 트리는 suffix·배지·묶음 요약만 둔다                                                                |
| 원격 조회와 busy      | 조회는 세션 busy 를 켜지 않고, 취소할 수 있는 op 만 붙인다                                                                                                                   |
| 문구                  | `S.tag.*` 섹션을 ko/en 에 함께 넣는다                                                                                                                                        |

## 핵심 git 명령

| 동작                                          | 명령                                                                                                                                                                                                             |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| push (하나·여럿 공통, 청크 ≤256KiB/1,000 ref) | `push --porcelain --progress --no-follow-tags --end-of-options <r> refs/tags/<n>:refs/tags/<n>…`                                                                                                                 |
| 원격 삭제                                     | 조회 `ls-remote --tags <r> refs/tags/<n> 'refs/tags/<n>^{}'` (50개 넘으면 전체 조회) 다음 `push --porcelain --no-follow-tags --force-with-lease=refs/tags/<n>:<oid> --delete --end-of-options <r> refs/tags/<n>` |
| 로컬 삭제                                     | `update-ref --stdin` 트랜잭션 (`delete refs/tags/<n> <oid>`). undo 1개, 라벨 `tag -d v1 v2 (+N)`                                                                                                                 |
| 원격 상태                                     | `ls-remote --tags <r>` (`--refs` 금지, `^{}` 필요). 로컬 쪽은 이미 읽는 `%(*objectname)`(`crates/mgit-git/src/cmd/refs.rs:9`)에 내부 `RefLabel.tag_object` 를 더해 비교한다. git 을 새로 실행하지 않는다         |
| 가져오기                                      | `fetch --porcelain --progress --no-tags --no-prune --no-write-fetch-head --end-of-options <r> refs/tags/a:refs/tags/a…` (맞추기는 `+`)                                                                           |

**두 쪽 삭제의 순서**: 고른 원격을 모두 먼저 처리한다. 모든 원격에서 deleted 나 alreadyAbsent 가 나온 tag 만 로컬에서 지운다. 결과를 알 수 없으면 `unknown` 으로 두고 실패로 단정하지 않는다.

**오류 분류 순서** (`crates/mgit-model/src/hint.rs`): `StaleInfo` → `non-fast-forward`·`fetch first` 의 NFF → `(already exists)` 의 `RemoteTagExists` → `[remote rejected]` 의 `RemoteRejected` → `failed to push some refs` 의 NFF(마지막 대비책). 지금은 `hint.rs:71` 이 `failed to push some refs` 만 보고 NFF 로 판단해서, tag 거부에도 강제 push 대화상자가 뜬다.

**원격 상태 캐시 무효화**

| 사건                    | 처리                                   |
| ----------------------- | -------------------------------------- |
| 앱의 push·삭제·가져오기 | porcelain 결과로 ref 단위 패치         |
| 수동·자동 fetch, pull   | 로컬 tag 집합이 바뀐 경우에만 stale    |
| branch push             | `push.followTags` 일 때만 stale        |
| 원격 이름·URL 변경      | 읽을 때 `state().refs.remotes` 와 비교 |
| 늦게 끝난 조회          | `started_at < mutated_at` 이면 stale   |

**병렬이 가능한 이유**
- U 레인은 목 모드(`dev:web`)와 vitest 만 쓰고 Rust 를 빌드하지 않는다. 그래서 cargo 빌드는 R(와 B4 의 D)에만 몰린다.
- 레인끼리 같은 파일을 고치지 않는다.
  - `bindings.ts`·목은 R 이 소유한다. C2 가 끝난 뒤에는 U 가 목 장면 데이터를 고칠 수 있다.
  - i18n 은 U 가 소유한다. Rust 문구는 R 이 소유한다.
- B2 는 기능과 무관한 결함 수정이라 R 레인 앞쪽으로 당겼다. 중간에 멈춰도 이 수정은 남는다.
- C3a 는 `tag_list` 없이 기존 RefLabel 과 원격 상태로 시작하고, C3b 만 H3 을 기다린다.

# 부록: mt-plan 확장판 전문 (2026-11-23)

> mt-plan 이 mt-ta·mt-ux 검토를 거쳐 낸 원문이다. 위 본문(승인안)과 다르면 본문이 우선한다. 특히 문서 갱신 시점(본문은 Phase M 으로 모음)과 실행 순서(본문은 레인)가 다르다.


### 0. 요약

**범위**
- 사용자 결정에 따라 MVP 를 넘어 세 가지를 이번 범위에 넣었습니다.
  - 원격 tag 상태 표시와 가져오기
  - 모든 tag push
  - 일괄 처리와 정리
- 사용자가 끝날 때마다 바로 쓸 수 있는 세 단계로 나눴습니다.
  - **Phase A**: tag 하나를 push 하고, 지울 곳을 골라 지웁니다.
  - **Phase B**: 원격 상태(로컬에만 / 원격에만 / 같음 / 다름)를 확인하고 브랜치 칸에 표시합니다.
  - **Phase C**: 에디터 공간의 "태그" 문서에서 비교, 일괄 push·가져오기·삭제, 모든 tag push, 정리를 합니다.

**관리 화면 판단**
- 전용 화면이 필요해졌습니다. 상태 다섯 가지, 원격에만 있는 행, 원격별 비교, 다중 선택이 들어오면 브랜치 칸 트리로는 감당하기 어렵습니다.
  - 트리에서 클릭하면 commit 으로 이동합니다. 그래서 다중 선택과 충돌합니다.
  - 트리는 가상화되지 않았습니다(`BranchTree.tsx:312`).
- mt-ux 권장안은 **에디터 공간 "태그" 문서 + 트리 가벼운 강화**입니다. 화면 구조가 바뀌는 결정이라 미결 질문 1로 남겼습니다.

**검증 관문**
- 앞 계획의 관문 세 가지를 유지합니다.
  - 삭제에도 lease 가 적용되는지
  - 로컬에서만 지운 tag 가 fetch 로 다시 생기는지
  - `--no-follow-tags` 가 다른 tag 를 막는지
- 여기에 새 관문 19개를 더했습니다.
- 지금 판단 중 "추정"으로 표시한 git 동작은 실행해 보지 않았습니다. 관문 테스트를 통과하기 전까지는 확정이 아닙니다.

**새로 찾은 기존 위험**
- 사용자 설정에 `fetch.pruneTags=true` 가 있으면, 5분마다 도는 자동 fetch 가 아직 push 하지 않은 로컬 tag 를 말없이 지웁니다.
- 자동 fetch 는 undo 대상이 아니라 되돌릴 수도 없습니다(`man git-config`, `core.rs:755`).
- 미결 질문 2로 남겼습니다.

이번 작업에서 바꾼 파일은 없습니다. 빌드·테스트도 돌리지 않았습니다. mt-ta·mt-ux 재검토도 같은 읽기 전용 제약으로 진행했습니다.

### 1. 문제와 성공 기준

**문제**
- 앱에서 만든 tag 를 원격으로 보낼 수 없습니다.
  - Push 는 `refs/heads` 만 보냅니다(`sync.rs:174`).
  - 프런트는 늘 `tags:false` 를 보냅니다(`session-store.ts:2573`).
- tag 삭제는 로컬 전용입니다.
- 원격 tag 가 어떤 상태인지 알 수 없습니다. git 에는 원격 tag 추적 ref 가 없습니다.
- 명세 BR-06 의 "푸시"가 미구현입니다. 사용자 문서 세 곳은 "기능이 없다"고 안내합니다.

**대상 사용자**: 저장소 탭에서 release tag 를 만들고 원격과 맞추는 개발자입니다. 원격이 여러 개(fork 의 origin·upstream)이거나 tag 가 수천 개인 저장소도 포함합니다.

**성공 기준**
1. **(A)** 로그나 브랜치 칸에서 tag 하나를 고른 원격으로 push 할 수 있습니다. 터미널이 필요 없습니다.
2. **(A)** 로컬만, 원격별, 둘 다 중에서 골라 지울 수 있습니다.
   - 확인한 뒤 원격 tag 가 바뀌었으면 지우지 않습니다.
   - 원격 tag 가 로컬과 다르면 두 commit 을 보여 주고 확인을 받습니다.
   - 일부만 성공하면 무엇이 바뀌고 무엇이 남았는지 알립니다. 남은 쪽은 다시 시도할 수 있습니다.
3. **(B)** 명시적으로 "원격 확인"을 하면 다음이 보입니다.
   - 로컬 tag 마다 push 안 됨 / 다름 표시
   - 원격에만 있는 tag 개수와 마지막 확인 시각
   - 확인 실패 상태
   - 앱의 push·삭제·가져오기 결과는 네트워크를 다시 쓰지 않고 표시에 반영됩니다.
4. **(C)** 태그 문서에서 다음을 할 수 있습니다.
   - 원격 하나를 골라 비교하고, 검색·필터·정렬합니다.
   - 여러 tag 를 골라 push·가져오기·삭제합니다.
   - tag 별 결과를 보고, 실패한 것만 다시 시도합니다.
   - 모든 tag push 는 "로컬에만 있는 목록을 검토한 뒤 보내기"로 합니다.
   - 원격에 없는 로컬 tag 를 골라 정리합니다.
5. 기존 branch push 의 non-fast-forward 흐름이 그대로입니다. 서버 거부에는 강제 push 대신 서버 사유가 보입니다(사용자 결정 4).
6. tag 수천 개 저장소에서 다음 기준을 지킵니다. 측정 결과 기준을 넘으면 지연 조회를 도입합니다.
   - 문서 목록 스크롤과 검색이 끊기지 않습니다.
   - 원격 상태 보고 크기가 2MB 이하입니다.
   - IPC 시간이 100ms 이하입니다.
7. ko/en 문구, 사용자 문서 3곳, 명세가 단계마다 실제 동작과 일치합니다.

### 4. mt-ta·mt-ux 판단 요약, 조정, 결정 목록

#### mt-ta 핵심 (근거 파일:줄)

**캐시와 무효화**
- 캐시는 `CoreInner` 에 `common_dir` 키로 둡니다. `write_locks` 와 같은 방식입니다(`core.rs:166-176`).
- 원격 이름이나 URL 이 바뀐 것은 읽을 때 `state().refs.remotes` 와 비교해서 알아냅니다. 감시와 재조회가 원격 목록을 이미 다시 읽기 때문입니다(`mgit-watch/src/classify.rs:47`, `refresh.rs:159`).
- **무효화 규칙**

| 사건                  | 처리                                           |
| --------------------- | ---------------------------------------------- |
| 앱의 push·원격 삭제   | porcelain 결과로 ref 단위 패치                 |
| 결과를 알 수 없는 ref | stale                                          |
| 가져오기              | 원격 항목 확정                                 |
| 수동·자동 fetch, pull | **로컬 tag 집합이 바뀐 경우에만** stale        |
| branch push           | `tags` 나 `push.followTags=true` 일 때만 stale |
| 늦게 끝난 조회        | `started_at < mutated_at` 이면 stale 로 반영   |
- "fetch 뒤 무조건 stale"은 기각했습니다. 자동 fetch 가 5분마다 돌기 때문에 표시가 늘 켜집니다.

**대용량**
- 로컬 비교에 git 을 새로 실행하지 않습니다. 재조회가 이미 `%(*objectname)` 을 읽으므로(`cmd/refs.rs:9`) 내부 `RefLabel` 에 `tag_object` 필드만 더합니다. DTO 는 바뀌지 않습니다(`dto.rs:161`).
- IPC 보고서는 **개수 요약과 "같음"이 아닌 항목만** 보냅니다.
- 프런트는 `RefsChanged` 때 `remote_tags(refresh=false)` 를 디바운스해서 부릅니다. tag 표시가 보일 때만입니다.

**porcelain 출력**
- 결과 표는 stdout 으로 나옵니다(`man git-push` OUTPUT).
- 지금 `run_write_in` 은 종료 코드가 0이 아니면 stdout 을 버립니다(`write.rs:314-328`). 그래서 `keep_failed_output` 과 `WriteResult.status` 가 필요합니다.
- 청크 사이에 op 를 닫지 않는 플래그도 필요합니다. 지금 `finish_op` 는 명령 하나가 끝날 때마다 닫습니다(`write.rs:333-354`).
- ARG_MAX 는 1,048,576 입니다.

**일괄 처리와 가져오기**
- 일괄 원격 삭제는 명령 하나에 lease 를 여러 개 걸 수 있다고 봅니다(`man` 249행). ref 마다 따로 적용되는지는 G3 로 확정합니다.
- 로컬 일괄 삭제는 `update-ref --stdin` 입니다. 한 트랜잭션이고 undo 하나입니다.
- 가져오기는 `--no-tags` 가 꼭 필요합니다. 없으면 자동 따라오기로 다른 tag 까지 받습니다. `--no-prune` 은 `fetch.prune` 설정에 대한 방어입니다.

**새로 찾은 위험**: `fetch.pruneTags` 가 켜져 있으면 자동 fetch 가 로컬 tag 를 지웁니다.

#### mt-ux 핵심

**관리 화면 후보 비교**

| 기준 | 트리 강화                                                                 | 모달                                  | Git 도구 창 탭                                                 | 에디터 문서                                                                                                                           |
| ---- | ------------------------------------------------------------------------- | ------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 판단 | 기각                                                                      | 차선                                  | 기각                                                           | **권장**                                                                                                                              |
| 이유 | 클릭이 commit 이동이라 다중 선택과 충돌하고, 비가상 트리는 행을 전부 그림 | 일괄 처리는 되지만 로그와 트리를 가림 | 폴더 탭으로 가면 아래 창 전체가 숨겨짐(`app-store.ts:213-217`) | 로그를 보면서 관리, 개요 탭 선례(결과 문서 `:15`), 새 포커스 영역 없음, 가상 목록 선례 `useVirtualTree`·`FolderCommitTree.tsx:98-106` |

**역할 분담**
- 트리와 로그 메뉴: tag 하나 작업과 상태 한눈에 보기
- 태그 문서: 비교, 원격에만 있는 tag, 일괄, 정리, 모든 tag push, 결과 보고
- 두 화면이 같은 코어 캐시를 읽으므로 정보가 엇갈리지 않습니다.

**대화상자와 결과 보고**
- 공용 대화상자에 네 가지를 더합니다.
  - prompt 에 `danger`, Enter 막기, `items`
  - confirm 에 두 번째 선택지 노출. 부품은 이미 지원합니다(`ConfirmDialog.tsx:17`, `:87`).
- 결과 칸은 실패만 남깁니다. 문서 안 작업은 토스트를 띄우지 않습니다.
- 모든 tag push 는 별도 확인창 대신 문서 안 흐름으로 합니다. `PromptDialog` 체크 목록은 가상화되지 않아 수천 개를 다룰 수 없습니다.

| 원격 조회와 busy                                 | 잠금 없는 `run_network_read`                           | busy 를 켜지 않기를 요청                  | **busy 를 켜지 않고 op 만 붙입니다.** 코어 `begin_operation` 은 op 를 맵으로 관리해 동시에 여러 개가 가능합니다(`core.rs:926`, `session-store.ts:1588`). 오래 걸린 작업 토스트는 조회 op 종류에서 끕니다 |
| tag 상세                                         | `tag_detail` 단건 포함                                 | 툴팁은 메시지 첫 줄과 tagger, 전체는 후속 | **목록용 `tag_list` 한 번(종류·날짜·commit 제목·tag 제목·tagger)만 포함합니다.** 단건 상세와 서명 검증은 후속입니다. 수천 개에서 `%(contents:signature)` 는 무거워 "서명" 열은 넣지 않습니다             |
| 강제 덮어쓰기                                    | lease 덮어쓰기 push 는 제외, "원격 것으로 교체"는 포함 | 맞추기 두 동작                            | **맞추기 두 동작으로 합니다(C5, 잘라도 됨).** `--force` 메뉴는 없습니다                                                                                                                                  |

### 6. 단계와 슬라이스, 검증

**공통 규칙**
- 슬라이스 하나가 커밋 하나이고, 각각 독립적으로 검증합니다.
- 작업 브랜치는 `master` 에서 새로 만듭니다(예: `feat/tag-management`).
- cargo·pnpm 은 샌드박스를 해제하고 실행합니다.
- git 동작 검증은 Rust 통합 테스트 안에서만 합니다(bare 원격 tempfile).

**슬라이스마다 기본으로 실행할 명령**
- Rust 슬라이스: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, 해당 `cargo test -p …`
- TS 슬라이스: `pnpm typecheck`, 해당 `pnpm exec vitest run <파일>`, `pnpm lint`

**의존 순서**
- 같은 단계 안에서 코어 → IPC·목 → 스토어·화면 → 문서 순서는 이 순서대로만 진행합니다.
- A5(공용 대화상자)와 B4(벤치)는 다른 슬라이스와 파일이 겹치지 않아 병렬로 진행할 수 있습니다.

### 8. 사용자에게 물을 미결 질문 (2개)

**1. tag 관리 화면을 어디에 둘까요?** (Phase C 의 C3·C4 형태가 정해집니다. Phase A·B 와는 무관합니다)
- (a) **에디터 공간의 "태그" 문서 탭 [권장]**: 아래 로그를 보면서 위에서 관리하고, 행을 누르면 로그가 그 commit 으로 갑니다. 폴더 탭 "개요" 표와 같은 방식이라 새 포커스 영역이 없고, 가상 목록으로 tag 수천 개를 다룰 수 있습니다.
- (b) 모달 관리자: 구현이 조금 단순하지만 로그와 트리를 가립니다.
- (c) 아래 Git 도구 창의 새 탭: 로그와 번갈아 봐야 하고, 폴더 탭으로 가면 아래 창 전체가 숨겨지는 결함이 있습니다.

**2. 사용자가 git 설정에 `fetch.pruneTags=true` 를 켜 둔 경우, 5분 자동 fetch 가 원격에 없는 로컬 tag(아직 push 하지 않은 것 포함)를 지우게 둘까요?** (Phase B 의 B2 슬라이스 여부가 정해집니다)
- (a) **자동 fetch 에만 `--no-prune-tags` 를 붙여 백그라운드에서는 지우지 않음 [권장]**: 수동 fetch 는 설정을 따릅니다. 자동 fetch 는 undo 대상이 아니라 되돌릴 수 없습니다. 자동 fetch 가 저장소 로컬 `core.sshCommand` 를 쓰지 않는 기존 보수적 원칙과도 맞습니다.
- (b) 사용자 설정 그대로 둠: 설정한 사람의 의도를 존중하지만, 태그 문서에서 만든 tag 가 5분 안에 사라질 수 있습니다.
