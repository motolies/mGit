# 반응성 개선 구현 결과 — 브랜치 비교와 UI 전반

기준: 2026-11-27~28 · 브랜치 `perf/responsiveness`(시작 `0250828` = `feat/multirepo-editor-batch1`, 끝 `0005ea6`) · push·버전 변경 없음.

"전반적인 퍼포먼스를 올리고 싶다. 브랜치 비교도 느리고 UI 동작도 느린 느낌"이라는 요청에서 출발했다. 릴리스 앱과 개발 빌드 모두, 비교의 모든 순간(처음 열 때·파일 diff·스크롤·자동 갱신)과 UI 네 영역(탭·저장소 전환, 스크롤, 편집기, 폴더 탭)이 느리다는 답을 받았고, 결함 두 건(파일 비교 창이 계속 깜빡임, 브랜치를 고를 때 글자가 작고 이름이 잘림)이 함께 보고됐다. 폴더 탭 하나에 저장소는 10~30개다. 진행 중에 사용자가 실제 앱을 쓰며 diff 스크롤 버벅임을 보고했고, 커서 줄을 없애고 다음 변경을 변경 덩어리 단위로 바꾸자고 요청했다.

## 1. 한눈에

- 1~2라운드의 느림은 코어(Rust)가 아니라 **화면 쪽 구조와 한 군데의 git 프로세스 남발**이었다. 기존 벤치가 전 항목 통과였던 것은 합성 저장소 + 목 데이터 + Chromium 기준이고 편집기·비교 시나리오가 없었기 때문이다.
- 그 뿌리는 세 가지다.
  - 파일을 하나라도 열어 두면 **2초마다** 편집기 저장소의 전역 버전이 올라 워크스페이스 전체가 다시 그려지고, 파일 비교 창은 그 신호로 목록과 diff 를 통째로 다시 받았다.
  - "현재 로컬 내용과 비교"의 파일 목록이 **경로마다 git 을 1~2개씩 차례로** 띄웠다.
  - 작은 상태 변화가 앱 루트·동작 목록·스토어의 새 참조를 거쳐 **화면 전체 다시 그리기**로 번졌다.
- 고치기 전에 측정 수단부터 만들었고(실제 앱 기록기, 비교 벤치, 화면 시나리오), 모든 수정은 전후 수치와 "고치기 전 코드에서 실패하는 테스트"로 고정했다.
- **정정**: 3라운드의 E(diff 줄 memo)·F(휠 처리)는 Chromium 재현을 근거로 고쳤지만 **실제 앱의 스크롤 버벅임을 고치지 못했다**. 실제 앱(WKWebView)에서 한 프레임의 약 0.1초는 스크립트가 아니라 브라우저의 배치였고, 같은 화면의 배치가 WebKit 에서 215~242ms·Chromium 에서 0.1~0.3ms 라 Chromium 측정은 이 비용을 잡지 못한다(8절).
- 실제 원인과 수정:
  - **H**: diff 본문이 스크롤 이벤트마다 커서 줄을 화면 첫 줄로 옮겨 DOM 을 바꿨다 → 스크롤로는 DOM 을 바꾸지 않게. 실제 앱 기록에서 거의 모든 스크롤 프레임이 약 110ms → 휠 약 600개 중 50ms 넘는 프레임 4개.
  - **I·K**: 세로 flex 부모 안의 `height:100%` 가 겹겹이 쌓여 WebKit 이 배치를 문서 뿌리부터 겹마다 다시 했다 → `flex: 1 1 0` 으로 풀고(`d84eda9`), 영역 내용 단위에 `contain: layout size` 경계(`1deb206`). WebKit 실험실(headless)에서 폴더 비교 diff 의 영역 안 배치가 242 → 16(사슬 풀기) → 0ms(경계)(상위가 전후 빌드를 따로 띄워 직접 잼).
  - **L**: 변경 위치 띠의 겹친 표시, 구간 머리 줄 높이가 어림값과 1px 달라 스크롤 중 행을 고쳐 쓰던 것.
- **사용자 요청으로 바뀐 동작(J)**: diff 본문에 커서 줄이 없다. 방향키·Space 는 스크롤만 하고, 키보드로 줄을 고르거나 되돌리지 않는다(사용자가 "함께 없앰"을 골랐다). 다음/이전 변경은 `@@` 구간이 아니라 빨강·초록 변경 덩어리 단위로 옮긴다(5절).
- 처음 보고된 결함 두 건과 진행 중 보고된 diff 스크롤 버벅임(2절)을 고쳤다. **배치 수정(K) 뒤의 실제 앱 수치는 아직 없다** — 사용자 화면이 잠겨 잴 수 없었다. 같은 엔진(Playwright WebKit, headless)으로 대신 확인했고, 실제 앱 확인 목록은 9절이다.

## 4. 전후 수치

수치의 출처가 넷이라 섞지 않는다.

- **목 화면·코어**(4.1): 프로덕션 목 빌드를 Chromium 에서 잰 화면 수치(`bench/frontend-measure.js`, 1400×900)와 릴리스 빌드의 `mgit-bench`·통합 테스트. 시간은 대부분 한 프레임(16.7ms) 근처라 **횟수**로 판정한다.
- **실제 앱 기록**(4.2): 사용자가 `pnpm dev --release`(Rust 는 릴리스, 화면은 개발 React)로 쓴 WKWebView 의 `perf.jsonl`.
- **WebKit 실험실**(4.3): Playwright WebKit(headless)으로 목 프로덕션 빌드를 연 강제 배치 시간. 실제 앱보다 느리게 나온다(같은 화면에서 실험실 약 0.23초, 실제 앱 약 0.1초).
- **WebKit 동작 확인**(4.4): 같은 headless WebKit 에서 휠 입력으로 잰 프레임.

측정 조건과 전체 표는 `bench/README.md` 의 해당 절에 있다.

## 5. 달라진 동작

기능을 더한 것은 없지만, 아래는 사용자가 알아챌 수 있는 변화다.

- 비교 화면의 기준·대상 칸에서 **고르는 즉시 다시 비교**한다. 방향 전환·공통 조상(three-dot)도 바로 적용된다. "비교 새로고침"은 같은 ref 를 다시 해석하는 용도만 남는다. "원격 정보 가져온 뒤 비교"가 고른 값을 무시하던 어긋남이 없어졌다.
- 선택 칸의 목록에서 stash 는 뺐다(직접 입력으로는 쓸 수 있다).
- "커밋 차이" 목록은 펼칠 때 조회한다. 브랜치↔브랜치 비교 탭으로 돌아오면 다시 조회하지 않고 마지막 결과를 보인다("비교 새로고침"은 다시 조회).
- 창으로 돌아온 지 5초 안에 다시 돌아오면 갱신을 건너뛴다. 그동안 파일 트리·폴더 요약·미리보기 그림·로컬 비교가 최대 5초 낡을 수 있다(git 상태는 감시가, 편집기는 2초 검사가 잡는다).
- 편집기에 열려 있지만 보이지 않는 파일은 창 포커스 때 표지만 확인하고, 그 탭을 열 때 원문을 읽는다.
- 저장 뒤에는 파일 트리 전체를 다시 읽지 않고 그 파일의 디렉터리만 다시 읽는다. Blame·HEAD 원문은 저장으로 다시 묻지 않는다.
- 창 포커스·주기 재조회 같은 배경 갱신에서는 새로고침 단추가 잠기지 않고 "불러오는 중" 표시가 깜빡이지 않는다(사용자가 누른 새로고침은 그대로 표시).
- 편집기에 열지 않은 파일의 외부 변경은 로컬 비교 창에서 창 포커스 때와 보이는 동안 5초마다 확인한다(예전에는 2초 주기가 우연히 잡아 줬다).
- 폴더 전체를 훑는 배경 읽기(요약·브랜치·변경·타임라인 로드·자동 fetch 뒤 읽기)는 git 읽기 8칸 중 7칸까지만 쓴다. 사용자가 누른 읽기가 기다리지 않는 대신 전체 갱신이 약 6% 늦어진다(`RunnerConfig::max_concurrent_bulk_reads`).
- **받아들인 한계**: 파일 하나 비교에서 권한(모드)만 바뀐 파일은 "차이 없음"으로 보인다. 예전에는 목록에 나오고 빈 diff 가 보였다. 문서 응답에 모드가 없어 IPC 계약을 바꿔야 가릴 수 있다.

diff 화면(F, 사용자 요청 J, 그 뒤의 L):

- **커서 줄이 없다.** 줄 위아래의 옅은 줄도, 줄을 누른 뒤 키를 누르면 뜨던 반쪽 줄의 테두리도 없다. 줄을 눌러도 포커스는 본문 하나에 남는다.
- **방향키·PageUp·PageDown·Home·End·Space 는 본문을 스크롤만 한다.** 키보드로 줄을 고르거나(Space·`⇧`+방향키) 되돌리지(작업 트리 diff 의 Enter) 않는다 — 사용자가 "커서로 하던 키보드 조작은?" 에 "함께 없앰"을 골랐다(보이지 않는 줄에 stage·되돌리기가 실행되는 위험). 줄·블록은 체크 상자와 되돌리기 단추, hunk 는 머리 줄 단추로 다룬다. ← → 로 좌우 쪽을 바꾸지도 않는다.
- **다음/이전 변경(F7·⇧F7)은 `@@` 머리 줄이 아니라 빨강·초록 변경 덩어리 단위**로 멈춘다. 한 구간 안에 떨어진 변경이 둘이면 두 번 멈추고, 덩어리 위에 문맥 3줄을 남긴다. 스크롤해 마지막으로 간 덩어리가 화면 밖이면 다음은 화면 맨 위 줄부터 아래로 처음 나오는 덩어리, 이전은 맨 위 줄보다 위의 마지막 덩어리로 간다.
- 도구 모음의 `n / 전체` 와 오른쪽 변경 위치 띠도 덩어리 수다(한 구간에 덩어리가 여럿이면 전보다 커진다). 띠는 어디를 눌러도 그 높이에 가장 가까운 덩어리로 간다.
- `⌘A` 는 마지막으로 누른 쪽(좌우 보기의 왼쪽·오른쪽) 코드 전체를 고른다(예전에는 ← → 로 고른 쪽).
- 팔레트 이름이 "다음/이전 변경 내용 구간" 에서 "다음/이전 변경"(en: Next/Previous change)으로 바뀌었다. 동작 id 는 그대로다.
- 휠: 세로로 굴리는 휠은 브라우저 기본 스크롤이다. 가로 성분이 더 큰 휠과 Shift+휠만 아래 가로 막대를 옮긴다(한 제스처 안에서는 처음 정한 축을 지킨다).
- 구간 머리 줄의 높이가 엔진·확대율에 따라 1px 안팎 달라졌다(예: WebKit 100% 21 → 20px). "개행 없음" 줄은 0.75~1px 낮아졌다.
- 본문 전체 테두리(`.scroller:focus-visible`)는 남겼다. 본문을 누른 뒤 키를 누르거나 F7·⇧F7 로 옮기면 뜨고, 마우스 클릭만·도구 모음 단추·변경 위치 띠로는 뜨지 않는다(10절 "정할 것").

개발·테스트 프로필에만 있는 것: 팔레트(⌘⇧A)의 "성능 자가 진단 실행 (개발용)"(6절). 배포 프로필에는 없다.

## 7. 검증

- 슬라이스마다 작업자가 `pnpm lint`·`pnpm typecheck`·`pnpm test` 와(Rust 를 고친 경우) `cargo fmt`·`clippy`·`cargo test` 를 돌렸고, 합칠 때마다 상위가 합친 상태에서 다시 돌렸다.
- 새 테스트가 고치기 전 동작을 실제로 잡는지 확인했다. 상위가 임시 워크트리에서 수정을 되돌리거나 결함을 다시 넣어 확인한 것: 로컬 비교를 고치기 전으로 되돌리면 새 테스트 9개 중 8개 실패, 바뀐 것 없는 검사가 다시 알리게 하면 7개 중 3개 실패, 트리 행 배열을 렌더마다 새로 만들면 2개 중 2개 실패, H(DiffView 를 `998c06f` 로) 새 테스트 10건 중 7건 실패, J(`49985af` 로) 59건 중 19건 실패, L(`d84eda9` 로) diff-view 113건 중 4건 실패. 그 밖의 슬라이스는 작업자가 같은 방법으로 확인해 보고했다.
- 로컬 비교 일괄 조회는 고치기 전 구현을 테스트 전용으로 남겨, 까다로운 경로 묶음(링크, 모드, gitlink, 하위 저장소, glob 이름, 파일↔디렉터리, 초안 등)에서 두 구현의 결과가 같은지 견준다.
- 배치 수정(K)은 모양이 바뀌지 않았는지 `shape` → `compare` 로 견줬다(4.3).
- 화면 눈 확인: 목 모드에서 1400×900·960×600, 다크·라이트로 선택 칸·트리 가로 스크롤·탭의 ● 표시를 확인했다. 3라운드 뒤로는 headless WebKit·Chromium 으로 J(덩어리 이동·문맥 3줄·키 스크롤·테두리·마우스 경로)와 L(띠·머리 줄)을 확인했고, K 뒤 화면도 WebKit 스크린샷으로 봤다(스크린샷 `.playwright-mcp/perf-check/` 의 `j-webkit-*`·`l-webkit-*`, 사본 `plan/perf-responsiveness-영상/`, git 제외 대상).
- 최종 통합 검증(Rust 는 `6dc7e30` — 그 뒤로 Rust·IPC 바인딩 변경 없음, 화면은 끝 커밋 `0005ea6`. 상위가 직접 실행):

## 8. 실제 앱 기록과 정정 (3라운드, 2026-11-27~28)

### 8.1 첫 기록과 E

사용자가 `pnpm dev --release`(Rust 는 릴리스, 화면은 개발 React)로 띄운 앱을 쓴 첫 기록이다(4.2 의 기록 1).

| 구간                               | 기록                                                                                                              |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 가만히 둔 42분                     | 반복되는 IPC 0, 50ms 넘는 프레임 0                                                                                |
| 폴더 탭 열기                       | `folderSummaries` 205ms · `folderChanges` 222ms · `folderBranches` 345ms                                          |
| "현재 로컬 내용과 비교" 열기       | 긴 프레임 144·321·116ms                                                                                           |
| 비교에서 키보드로 파일 이동 (18번) | 입력 → 그리기 120~680ms(중앙값 약 315ms). 그중 `compareLocalDocument` 는 65~86ms, 키마다 100~110ms 프레임이 3~4개 |
| diff 스크롤                        | 135~136ms 프레임이 연속 7개                                                                                       |
| 로컬 비교의 느린 재검사            | 10초 간격, `compareLocalFiles` 79~276ms                                                                           |

1~2라운드가 줄인 것(쓸데없는 재조회·다시 그리기)은 가만히 둔 구간에서 확인됐고, 남은 느림은 diff 화면(파일 이동·스크롤·열기)이었다. 목 화면이 이것을 못 잡아, 큰 목 문서(3,000줄·변경 40곳) + 개발 빌드 + CPU 4배 감속의 **Chromium** 에서 같은 모양(키마다 긴 프레임 3~4개, 스크롤 p95 125ms)을 재현해 줄 memo 등으로 고쳤다(E).

그 재현에서 비용의 큰 몫은 **개발 빌드에서만** 커졌다(개발 React 의 요소 디버그 정보와 StrictMode 의 두 번 렌더). 같은 문서·같은 감속에서 프로덕션 빌드는 고치기 전에도 스크롤 p95 16.7ms, 키마다 긴 프레임 1개였다. `pnpm dev --release` 의 체감은 설치본보다 나쁘게 나온다. 다만 8.2 의 배치 비용은 WebKit 실험실에서 프로덕션 목 빌드로도 재현됐다.

### 8.2 정정 — Chromium 재현이 놓친 것

- **E 의 스크롤 수정은 실제 원인이 아니었다.** 기록 2 에서 휠 긴 프레임은 61건·중앙값 110ms 로 그대로였다. 재는 시나리오 `diffScroll` 이 `scrollTop` 을 직접 바꿔 휠 이벤트가 일어나지 않았다(재현 방법이 실제 입력과 다른 측정의 잘못).
- **F 의 휠 수정도 사용자의 원인이 아니었다.** 가로 성분이 섞인 휠의 처리 비용은 Chromium 에서 재현해 없앴지만, 기록 3 에서 사용자의 휠 840개 중 가로 성분이 있는 것은 54개였다(대각선 제스처의 결함만 고쳤다). 실제 원인이던 `onScroll` 의 커서 줄 이동(8.3 의 H)은 F 에서 코드를 보고도 Chromium 에서 전후가 같다는 이유로 남겼던 곳이다.
- 기록 3 이 원인의 성격을 갈랐다: 긴 프레임에서 React 렌더는 1~4ms(1~3%)였고, 스크립트가 거의 없는 hover 한 번도 그려지기까지 약 0.1초였다. 한 프레임의 값은 **스크립트가 아니라 브라우저 쪽**이었다.
- 표본 조사가 그 정체를 보였다: 바쁜 시간의 절반이 겹친 flex 의 배치였고, 스크립트의 동기 크기 읽기가 그것을 강제했다(4.2).
- 왜 Chromium 은 못 잡는가: 같은 화면에서 흐름 속 변경 하나의 배치가 WebKit 215~242ms, Chromium 0.1~0.3ms 다(4.3). WebKit 은 세로 flex 안의 `height:100%` 겹마다 하위 트리를 다시 배치해 겹마다 값이 약 두 배가 된다. 1~3라운드가 줄인 스크립트 쪽 낭비는 실제였지만 체감으로 잘 이어지지 않은 까닭이다.

### 8.3 그 뒤에 고친 것

- **H**(`fd680fa`·`0ddb54f`, 워크트리 레인): 사용자의 화면 기록에서 스크롤할 때 맨 위 줄을 감싼 파란 네모(커서 줄)가 따라 움직였다. 본문 `onScroll` 이 스크롤 이벤트마다 커서 줄을 옮겨 DOM 을 바꿨고, 그때마다 약 0.1초의 배치가 돌았다. 스크롤로는 DOM 을 바꾸지 않게 했다(jsdom 계수: 줄을 넘는 스크롤 7번의 행·본문 속성 변경 21 → 0). 자가 진단 2 에서 휠 약 600개 중 긴 프레임 4개(모두 탐침이 바뀌는 순간)가 됐다.
- **G**(`aef32de`·`49985af`·`0005ea6`): 실제 앱을 사람 없이 재려고 자가 진단을 넣었다. 첫 실행은 화면 잠금으로 무효였다.
- **I·K**(`3ff78f3`·`d84eda9`·`1deb206`): 워크트리 레인이 headless WebKit 실험실에서 실제 앱과 같은 현상(편집기 영역 안 배치 215~225ms, 루트 사용자 정의 속성 225ms)을 재현했다. 원인은 세로 flex 안의 `height:100%` 겹이었고, 겹을 `flex: 1 1 0` 으로 풀어 화면마다 약 5~17ms 로, 영역 내용에 `contain: layout size` 경계를 둬 영역 안 변화를 0ms 로 줄였다(4.3). `contain: strict` 는 효과가 없었고, 분할 패널 자체에 걸면 루트 쪽이 약 410ms 로 나빠져 쓰지 않았다.
- **J**(`7b48e70`·`db68762`·`47ab319`): 사용자 요청으로 커서 줄을 없애고 다음 변경을 덩어리 단위로 바꿨다(5절).
- **L**(`a165749`·`6351668`): J 를 WebKit 에서 확인하다 찾은 두 가지 — 변경 위치 띠의 겹친 표시, 구간 머리 줄의 1px 어긋남(4.4).

## 10. 남은 것과 정할 것

정할 것:

- **본문 전체 테두리**(`.scroller:focus-visible`): 사용자가 지우라고 한 줄 단위 테두리와는 다른 것이라 남겼다. F7·⇧F7, 본문을 누른 뒤 키를 누를 때 뜬다. 없앨지 정한다.
- **GraphView 의 동기 다시 그리기**: `useFlushSync: false` 는 빈 행 프레임 때문에 넣지 않았다(3절). 시험해 본 대안은 화면 밖 여분 행(overscan)을 8 → 24 로 늘리는 것으로, 실험실에서만 프레임당 500px 스크롤까지 빈 프레임 0 이었다. 그래프 쪽 동기 다시 그리기는 휠 한 프레임에 배치를 두 번 부르는 경로로 지목됐지만(워크트리 레인 분석), 영역 경계(K) 뒤에는 그 배치가 영역 안에 갇혀 실험실 0~1ms 다. 실제 앱 재측정 뒤 볼지 정한다.
- **레인 워크트리·브랜치 정리**: 병렬 레인 워크트리 `_worktrees/perf-responsiveness/core`(브랜치 `perf/responsiveness-core`, 끝 `bff519c`)가 남아 있다. `git cherry` 로 보면 이 브랜치에만 있는 커밋 4개는 모두 같은 내용으로 작업 브랜치에 있다. 정리는 사용자 확인 뒤에 한다.
- **master 병합·push**: 작업 브랜치는 `feat/multirepo-editor-batch1` 위에 쌓여 있다. 병합·push 는 하지 않았다.

다음 후보:

- **새 diff 문서를 그리는 프레임**: 파일을 옮기면 본문 마운트와 구문 강조가 한 프레임에 든다(Chromium 개발 빌드·CPU 4배에서 117~166ms, 프로덕션은 58~65ms). 실제 앱 기록 2 에서도 키마다 100~110ms 프레임 3개가 남았고, K 뒤의 값은 아직 없다. 줄이려면 옛 문서를 남긴 채 읽는 중으로 보이거나(지금은 다른 파일이면 바로 가린다), 강조를 뒤로 미루거나, 화면 밖 여분 줄을 줄여야 한다. 동작이 달라지는 선택이라 K 뒤 실제 앱 기록을 보고 정한다.
- **탭 전환**: 상단 탭을 바꾸면 워크스페이스를 통째로 다시 만든다(Git 로그 칸 368~545 컴포넌트 새로 마운트). Chromium 에서 15~18ms 라 손대지 않았다. 실제 앱 기록에서 길게 나오면 다음 후보다.
- **stage 등 쓰기 동작에 남은 다시 그리기**: 브랜치 칸(툴바·행 단추의 비활성이 바쁨을 따름), Commit 도구 창, 로그 칸의 필터 바 잠금. 실제로 달라지는 표시이거나 구조를 더 바꿔야 하는 곳이다.
- **워크스페이스 재렌더가 편집기 공간으로 번짐**: `RepoWorkspace` 는 status 의 항목·요약(Project 트리 장식용)과 탭 고정에, `FolderWorkspace` 는 트리 선택에 다시 그려지고, 편집기 공간이 그 자식이라 함께 그려진다(폴더 탭 ↓ 이동에 트리 85·편집기 47, 다른 파일 저장에 열어 둔 diff 쪽 82씩). 편집기 공간을 memo 경계로 떼고 안정된 콜백을 넘기면 줄일 수 있지만 구조 변경이 커서 멈췄다.
- **폴더 탭 일괄 작업 중의 다시 그리기**는 재지 않았다.
- **폴더 전부 읽기의 중복**: 저장소 20개 기준 git 180개 중 꼭 필요한 것은 약 40개다(저장소 판별 3회, status 2회, HEAD 읽기 중복). 벤치로는 기준 안(172ms)이라 두었다.

- **저장 뒤 남은 조회**: status 이벤트가 부르는 서브모듈·워크트리 다시 읽기, 저장 뒤 표지 확인의 원문 1회 읽기.
- **시작 시간**(로그인 셸 PATH 탐색이 setup 훅 안, 탭 복원 직렬), **개발 빌드 프로필**: 손대지 않았다. 실제 앱의 첫 기록(`pnpm dev --release`, 저장소 탭 하나 복원, 시작 뒤 1.2초)에서 시작 때 함께 나간 IPC 15종(`conflictRadar`·`signingInfo`·`commitTemplates`·`backups`·`modules`·`listStashes` 등)이 모두 약 180~200ms 에 한꺼번에 끝났다. 명령마다 걸리는 시간이 아니라 공통 대기로 보인다(첫 그리기로 화면 스레드가 바쁘거나, 탭 열기의 git 읽기 뒤에 줄을 선 것 — 원인은 가리지 않았다). 시작 구간을 볼 때의 출발점이다.
