# 빌드·테스트

소스에서 mGit 을 빌드하고 실행하고 검사하는 방법입니다. 처음 한 번 할 일, 매번 할 일, 가끔 할 일 순서로 적었습니다.

기준: 브랜치 `feat/tag-management` · 커밋 `aedc0b6` · 2026-11-23

## 0. 한눈에

처음이면 준비물(1절)을 갖춘 뒤 저장소 루트에서 아래 세 줄을 차례로 실행합니다.

```bash
pnpm install   # 의존성 설치 — 처음 한 번, pnpm-lock.yaml 이 바뀌면 다시
pnpm dev       # 개발 실행 — 화면 개발 서버와 디버그 앱을 함께 띄웁니다
pnpm check     # 화면 쪽 검사 — lint + typecheck + test
```

Rust 쪽 검사는 한 줄입니다.

```bash
cargo fmt --all --check && cargo clippy --workspace --all-targets -- -D warnings && cargo test --workspace
```

새로 받은 클론에서 위 명령을 실제로 실행해 잰 시간입니다. 각 명령의 쓰임은 3절과 5절에 있습니다.

| 명령                             | 걸린 시간 | 조건                                                                     |
| -------------------------------- | --------- | ------------------------------------------------------------------------ |
| `pnpm install --frozen-lockfile` | 0.8초     | 이 Mac 에 이미 받아 둔 패키지 205개를 그대로 씀                          |
| `pnpm dev` — 앱 창이 뜨기까지    | 46초      | 클론 후 첫 실행. 이 가운데 Rust 컴파일이 41초                            |
| `pnpm dev` — 두 번째부터         | 5초       | 고친 것이 없을 때(Rust 컴파일 0.7초)                                     |
| `pnpm check`                     | 17초      | 테스트 137개 파일, 1,710개                                               |
| `cargo fmt --all --check`        | 0.4초     |                                                                          |
| `cargo clippy … -D warnings`     | 21초      | `pnpm dev` 를 한 번 실행한 뒤                                            |
| `cargo test --workspace`         | 1분 38초  | `pnpm dev`·clippy 를 실행한 뒤. 컴파일 27초, 테스트 596개(1개는 ignored) |

잰 기계는 Apple M4 Pro(14코어)·메모리 24GB·macOS 27.2.1 입니다. 처음 쓰는 Mac 에서는 npm 패키지와 Rust crate 를 내려받는 시간이 더 듭니다(재지 않음).

pnpm 명령 하나로 화면과 Rust 가 함께 빌드됩니다. 연결은 `package.json` 의 scripts 와 `apps/desktop/src-tauri/tauri.conf.json` 의 `build` 항목에 있습니다.

```text
pnpm dev
└─ pnpm -F @mgit/desktop tauri dev           (루트 package.json)
   ├─ beforeDevCommand: pnpm dev:web          → Vite 개발 서버 http://localhost:1420
   └─ cargo run (디버그 빌드)                 → target/debug/mgit-desktop
      └─ 앱 창이 http://localhost:1420 의 화면을 띄움

pnpm build
└─ pnpm -F @mgit/desktop tauri build
   ├─ beforeBuildCommand: pnpm build:web      → apps/desktop/dist
   └─ cargo build --release                   → .app·.dmg (패키징 문서)
```

`.app`·`.dmg` 를 만드는 `pnpm build` 는 [패키징](패키징.md)에서 다룹니다.

## 1. 준비물

빌드하려면 아래 도구가 필요합니다. 확인 명령을 터미널에서 실행해 버전을 봅니다.

| 도구                     | 버전              | 확인 명령                 | 설치                                                |
| ------------------------ | ----------------- | ------------------------- | --------------------------------------------------- |
| macOS                    | 15 이상           | `sw_vers -productVersion` | —                                                   |
| Xcode Command Line Tools | —                 | `xcode-select -p`         | `xcode-select --install`                            |
| Rust(rustup)             | stable, 최소 1.90 | `rustc --version`         | 아래 rustup 설치 명령                               |
| Node.js                  | 24                | `node --version`          | [nodejs.org](https://nodejs.org) 설치 파일          |
| pnpm                     | 11.20.0           | `pnpm --version`          | `corepack enable pnpm`                              |
| git                      | 2.45 이상         | `git --version`           | Command Line Tools 에 포함, 또는 `brew install git` |
| git-lfs                  | 선택              | `git lfs version`         | `brew install git-lfs`                              |
- Xcode Command Line Tools — 데스크톱 앱만 빌드하므로 Xcode 전체는 없어도 됩니다.
- Rust — rustup 공식 설치 명령입니다. 기본값으로 설치하면 rustfmt·clippy 도 함께 들어옵니다.

  ```bash
  curl --proto '=https' --tlsv1.2 https://sh.rustup.rs -sSf | sh
  ```

  저장소의 `rust-toolchain.toml` 이 stable 툴체인과 rustfmt·clippy 를 고릅니다. 최소 버전 1.90 은 루트 `Cargo.toml` 의 `rust-version` 입니다.
- Node.js — 저장소에 `engines`·`.nvmrc` 는 없습니다. Node 24 로 개발하고 검사했으므로 24 를 권합니다.
- pnpm — Node 24 에 들어 있는 corepack 으로 켭니다(`corepack enable pnpm`). 저장소 폴더 안에서는 루트 `package.json` 의 `"packageManager": "pnpm@11.20.0"` 을 보고 이 버전을 받아 씁니다. 2절에서 소스를 받은 뒤 그 폴더에서 `pnpm --version` 이 11.20.0 인지 봅니다.
- git — 앱은 시스템의 git 을 씁니다. 2.45 보다 낮으면 앱이 경고하고, 테스트(`cargo test`)도 git 으로 임시 저장소를 만들어 시험합니다.

## 2. 소스 받기와 첫 설치

소스를 받으려면 저장소를 clone 하고 의존성을 설치합니다. 예시 경로는 `~/work/mGit` 입니다.

1. 저장소를 받습니다.

   ```bash
   git clone <저장소 주소> ~/work/mGit
   cd ~/work/mGit
   ```

2. JavaScript 의존성을 설치합니다.

   ```bash
   pnpm install
   ```

- `pnpm-lock.yaml` 을 바꾸지 않고 그대로 설치하려면 `pnpm install --frozen-lockfile` 을 씁니다.
- `pnpm install` 은 npm 패키지만 받습니다. Rust crate 는 처음 `pnpm dev` 나 `cargo` 명령을 실행할 때 cargo 가 받습니다.

## 3. 개발 실행

앱을 소스에서 띄우려면 저장소 루트에서 실행합니다.

```bash
pnpm dev
```

1. Vite 개발 서버가 `http://localhost:1420` 에 뜹니다.
2. cargo 가 `mgit-desktop` 을 디버그로 빌드합니다. 처음에는 의존성까지 모두 컴파일해 오래 걸립니다(0절 표).
3. 터미널에 ``Running `…/target/debug/mgit-desktop` `` 줄이 나오고 앱 창이 뜹니다.

- 화면 코드(`apps/desktop/src`, `packages/*`)를 고치면 Vite 가 바로 창에 반영합니다.
- Rust 코드(`apps/desktop/src-tauri`, `crates/*`)를 고치면 `tauri dev` 가 알아채 다시 컴파일하고 앱을 다시 띄웁니다. 시작할 때 터미널에 감시하는 폴더가 `Info Watching … for changes` 로 나옵니다.
- 끄려면 터미널에서 `⌃C` 를 누릅니다.

### 경로를 넘겨 시작하기

시작하자마자 특정 폴더나 저장소를 열려면 경로를 넘깁니다.

```bash
pnpm tauri dev -- -- ~/work/acme-platform
```

- 첫 `--` 뒤는 cargo 에, 두 번째 `--` 뒤는 앱에 전달됩니다. 터미널의 `Running` 줄 끝에 경로가 붙어 있으면 앱까지 간 것입니다.
- `apps/desktop` 폴더에서는 `./node_modules/.bin/tauri dev -- -- <경로>` 도 같습니다.
- 앱은 실제로 있는 경로만 엽니다. 없는 경로와 `-` 로 시작하는 인자는 버립니다. 경로는 절대 경로로 줍니다(`~/…` 는 셸이 절대 경로로 바꿔 줍니다).

### 연습용 합성 폴더

실제 저장소 대신 시험해 볼 폴더가 필요하면 합성 폴더를 만듭니다.

```bash
bench/setup.sh folder 20 2000        # 저장소 20개 × 커밋 2,000개 → bench/repos/folder-20x2000
pnpm tauri dev -- -- "$PWD/bench/repos/folder-20x2000"
```

- `git fast-import` 로 만드는 가짜 이력입니다. 같은 인자면 늘 같은 커밋이 나옵니다.
- 원격 주소가 `https://example.invalid/…` 라서 fetch·push 가 어디에도 닿지 않습니다.
- `bench/repos/` 는 git 이 무시하는 폴더입니다. 이미 있는 저장소는 건너뛰므로 다시 만들려면 그 폴더를 지웁니다.
- 다른 크기·모양은 [bench/README.md](../bench/README.md#폴더-모드--여러-저장소-폴더-열기-w0-측정-기준선)의 "준비"에 있습니다.

### 개발 실행에서 알아 둘 것

- 디버그 실행은 시작할 때마다 `packages/ipc/src/bindings.ts` 를 다시 씁니다. Rust 쪽을 고치지 않았으면 내용이 같아서 `git status` 에 나오지 않습니다. 바뀌어 보이면 6절을 보세요.
- mGit 은 한 번에 하나만 뜹니다. 설치한 mGit 이 이미 떠 있으면 새로 뜬 디버그 앱은 넘긴 경로를 그 앱에 전달하고 바로 끝납니다(코드 기준, 실제로는 확인 전). 개발 실행 전에 설치한 앱을 끄세요.

> [!NOTE]
> 개발 실행과 설치한 앱은 같은 데이터 폴더 `~/Library/Application Support/io.github.motolies.mgit/` 를 함께 씁니다(identifier `io.github.motolies.mgit` 이 같음). 여기에 최근 목록·열린 탭·설정·창 크기가 있습니다. 그래서 `pnpm dev` 로 띄운 앱이 설치한 앱에서 열어 둔 실제 저장소 탭을 그대로 복원하고, 개발 실행에서 연 탭은 설치한 앱에도 나타납니다. 다시 켰을 때 복원되는 것은 [사용법 2.8](사용법/2-저장소와-폴더-열기.md#28-다시-켰을-때-돌아오는-것)에 있습니다.

> [!TIP]
> 고치는 중인 코드로 실제 저장소를 건드리고 싶지 않으면 합성 폴더를 경로로 넘겨 시작하고 그 탭에서만 시험하세요. 개발 실행에서 탭을 닫으면 설치한 앱을 다음에 켤 때도 그 탭은 돌아오지 않습니다.

## 4. 목 모드 — 코어 없이 화면만 보기

Rust 를 빌드하지 않고 화면만 보려면 목 모드로 브라우저에서 띄웁니다. 목 모드는 코어 대신 합성 데이터를 돌려주는 가짜 클라이언트를 씁니다.

1. 목 모드 개발 서버를 띄웁니다. `2000` 은 합성 그래프의 행 수입니다.

   ```bash
   VITE_MGIT_MOCK=2000 pnpm -F @mgit/desktop dev:web
   ```

2. 브라우저에서 `http://localhost:1420` 을 엽니다. 시작 화면이 나옵니다.
3. 장면을 고르려면 `VITE_MGIT_MOCK_SCENE` 을 함께 줍니다. 그 장면의 탭이 바로 열립니다.

   ```bash
   VITE_MGIT_MOCK=2000 VITE_MGIT_MOCK_SCENE=folder pnpm -F @mgit/desktop dev:web
   ```

| 장면       | 처음 열리는 탭                                 | 주로 보는 것                                                                                        |
| ---------- | ---------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| (없음)     | 시작 화면                                      | **저장소 열기…** 를 누르면 합성 그래프 저장소가 열림                                                |
| `folder`   | 폴더 탭 `/mock/acme-platform`(저장소 8개)      | 통합 로그, 폴더 Commit, rebase 충돌                                                                 |
| `repo`     | 저장소 탭 `/mock/storefront-web`               | branch·stash·워크트리·서브모듈·Pull Requests·Git 콘솔, tag(원격 `origin`·`upstream` 과 상태가 섞임) |
| `conflict` | 저장소 탭 `/mock/checkout-service`(merge 충돌) | 3-way 충돌 편집기, 삭제·수정 충돌                                                                   |

### 서버를 끄지 않고 바꾸기

브라우저 개발자 도구 콘솔에서 `localStorage` 값을 넣고 새로 고치면 장면과 목의 응답이 바뀝니다. 환경 변수보다 앞섭니다.

```js
localStorage.setItem('mgit.mock.scene', 'repo'); // folder | repo | conflict | none(시작 화면)
location.reload();
```

| 키                       | 값                                                         | 바뀌는 것                                                                             |
| ------------------------ | ---------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `mgit.mock.scene`        | `folder`·`repo`·`conflict`·`none`                          | 장면                                                                                  |
| `mgit.mock.gitVersion`   | 예: `2.54.0`                                               | 상태 바의 git 버전 글자                                                               |
| `mgit.mock.hosting`      | `github`(기본)·`none`·`noAccount`·`empty`·`error`·`gitlab` | Pull Requests 도구 창의 응답                                                          |
| `mgit.mock.superproject` | `1`                                                        | `storefront-web` 을 서브모듈로 엶                                                     |
| `mgit.mock.folderOps`    | `1`~`3`                                                    | 폴더 장면에 진행 중인 작업(merge 등) 추가                                             |
| `mgit.mock.tags`         | 예: `3000`                                                 | 저장소마다 합성 tag N개를 더함. 로컬·원격 상태가 고르게 섞임(tag 수천 개 화면 측정용) |

저장소 수·원격 브랜치 수 같은 크기 조절값은 [bench/README.md](../bench/README.md#재는-방법)의 표에 있습니다. 다 지우려면 `localStorage.clear()` 뒤 새로 고칩니다.

합성 tag 수만은 환경 변수가 먼저입니다. `VITE_MGIT_MOCK_TAGS=3000` 을 주고 띄우면 `mgit.mock.tags` 는 보지 않습니다.

### tag 실패 주입

저장소 장면의 tag 작업(push·원격 삭제·로컬 삭제·가져오기·덮어쓰기, 원격 tag 확인)은 기본으로 성공합니다. 실패를 보려면 개발자 도구 콘솔에서 `globalThis.__mgitMockTagFail` 에 객체를 넣습니다. 부를 때마다 읽으므로 새로 고치지 않아도 됩니다. 원격 자리의 값은 `true`(모든 원격) 또는 원격 이름 배열입니다.

```js
globalThis.__mgitMockTagFail = { deleteRemote: ['upstream'] }; // upstream 의 원격 삭제만 서버가 거부
delete globalThis.__mgitMockTagFail; // 끄기
```

| 키             | 값                    | 바뀌는 것                                                                                                         |
| -------------- | --------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `deleteRemote` | `true`·원격 이름 배열 | 그 원격의 원격 삭제를 서버가 거부함(사유 `pre-receive hook declined`). 로컬 tag 는 남음                           |
| `pushExists`   | tag 이름 배열         | 그 tag 의 push 가 이름 충돌로 거부됨. 장면의 `v2.3.1` 은 넣지 않아도 `origin` 에서 충돌함                         |
| `diverged`     | tag 이름 배열         | 원격 삭제에서 원격 것이 로컬과 다르다고 답함(다를 때 확인창이 뜸)                                                 |
| `auth`         | `true`·원격 이름 배열 | 그 원격과의 명령이 인증 실패로 거부됨. 원격 tag 확인은 **인증 실패** 로 보임                                      |
| `lookup`       | `true`·원격 이름 배열 | 그 원격의 조회가 연결 실패함(오프라인 흉내). 원격 tag 확인은 **연결 실패** 로 보이고, 원격 삭제·가져오기는 거부됨 |
| `stale`        | `true`·원격 이름 배열 | 그 원격의 확인 결과에 **오래됨** 이 붙음(목에는 바깥 변경이 없어 스스로는 오래되지 않음)                          |

### 다크로 보기와 끄기

- 툴바 오른쪽 **테마** 에서 **다크** 를 고릅니다. 콘솔에서 `localStorage.setItem('mgit.theme', 'dark')` 뒤 새로 고쳐도 됩니다. 처음 값은 브라우저(macOS)의 밝은·어두운 모드를 따릅니다.
- 끄려면 서버를 띄운 터미널에서 `⌃C` 를 누릅니다. 다른 터미널에서는 `lsof -ti tcp:1420 -sTCP:LISTEN | xargs kill` 로 끕니다.
- 목 모드와 `pnpm dev` 는 같은 1420 포트를 써서 동시에 띄울 수 없습니다.

### 목 모드의 한계

- 저장소 탭의 쓰기 작업(checkout·merge·stash·fetch 등)은 성공한 것처럼 보이지만 화면이 바뀌지 않습니다. 저장소 탭의 commit 은 오류가 납니다.
- 화면이 실제로 바뀌는 쓰기는 폴더 장면의 stage·unstage·commit 과 충돌 해결, 저장소 장면의 tag push·원격 삭제·로컬 삭제·가져오기·원격 tag 를 로컬 것으로 덮어쓰기입니다. tag 작업에도 Undo 는 없습니다.
- 최근 목록은 늘 비어 있습니다. 저장소 설정, 폴더 스캔, clone 진행, 인증 묻기는 볼 수 없습니다.
- 폴더 선택 창 대신 늘 `/mock/repo-<행 수>` 를 엽니다. 상태 바의 git 버전에는 `(mock)` 이 붙습니다.

> [!WARNING]
> `VITE_MGIT_MOCK` 은 빌드할 때 화면 코드에 박힙니다. `export VITE_MGIT_MOCK=…` 처럼 셸에 남은 채 `pnpm build` 를 하면 목 앱이 만들어집니다. 그 앱은 실제 저장소 대신 합성 데이터를 보여 주고, 그 안에서 한 작업은 저장소에 반영되지 않습니다. `pnpm dev` 의 앱 창도 같습니다. 빌드 전에 `echo $VITE_MGIT_MOCK` 가 비어 있는지 보고, 남아 있으면 `unset VITE_MGIT_MOCK VITE_MGIT_MOCK_SCENE` 으로 지웁니다. → [패키징 2절](패키징.md#2-만들기)

## 5. 테스트와 검사

커밋하기 전에 아래 1~4 를 이 순서로 돌립니다. 저장소에는 CI(GitHub Actions)가 없어 이 검사가 유일한 확인입니다. Windows 판이 필요해지면 CI 를 다시 붙여 확인합니다([패키징 9절](패키징.md#9-windows)).

| 순서 | 명령                                                    | 하는 일                                  | 걸린 시간 |
| ---- | ------------------------------------------------------- | ---------------------------------------- | --------- |
| 1    | `cargo fmt --all --check`                               | Rust 서식 검사                           | 0.4초     |
| 2    | `cargo clippy --workspace --all-targets -- -D warnings` | Rust lint. 경고도 실패로 봄              | 21초      |
| 3    | `cargo test --workspace`                                | Rust 테스트                              | 1분 38초  |
| 4    | `pnpm check`                                            | biome lint → tsc typecheck → vitest test | 17초      |
| —    | `cargo fmt --all`                                       | Rust 서식을 고침                         | —         |
| —    | `pnpm format`                                           | biome 로 화면 코드·문서 서식을 고침      | —         |

걸린 시간의 조건은 0절 표와 같습니다.

- 화면 쪽만 고쳤으면 4만, Rust 만 고쳤으면 1~3 만 돌려도 됩니다. `pnpm check` 는 `pnpm lint`·`pnpm typecheck`·`pnpm test` 를 차례로 부르므로 하나씩 따로 돌릴 수도 있습니다.
- `pnpm lint`(biome)는 마크다운 표의 정렬도 검사합니다. 문서만 고쳐도 돌리고, 틀리면 `pnpm exec biome format --write <파일>` 로 고칩니다. `claudedocs/` 는 검사에서 빠집니다.
- 테스트 하나만 보려면 `pnpm exec vitest run <파일 경로>`, `cargo test -p mgit-core <이름>` 처럼 범위를 줍니다.
- `pnpm test` 출력에 `Not implemented: HTMLCanvasElement's getContext()` 가 여러 번 나옵니다. 테스트 환경(jsdom)이 캔버스를 그리지 않아서 나오는 줄이고 실패가 아닙니다. 끝의 `Test Files … passed` 를 봅니다.
- `cargo test --workspace` 도 `packages/ipc/src/bindings.ts` 를 다시 씁니다(6절의 `pnpm gen:ipc` 와 같은 테스트가 들어 있음).

## 6. 가끔 하는 일

### Tauri 명령·DTO 를 바꿨을 때

화면이 부르는 Rust 명령이나 주고받는 타입을 바꿨으면 TypeScript 바인딩을 다시 만듭니다.

```bash
pnpm gen:ipc   # = cargo test -p mgit-desktop --lib export_bindings
```

- 필요한 때: `apps/desktop/src-tauri/src` 의 `#[tauri::command]` 함수, 또는 `specta::Type` 을 붙인 타입(`dto*.rs`·`commands_*.rs`·`events.rs` 등)을 더하거나 바꿨을 때입니다.
- 결과: `packages/ipc/src/bindings.ts` 가 새로 써집니다. 이 파일은 손으로 고치지 않습니다(파일 첫 줄에 적혀 있음). 창은 뜨지 않습니다. 이번에 잰 시간은 12초(`cargo test` 뒤)입니다.
- `pnpm dev` 와 `cargo test --workspace` 도 같은 파일을 쓰므로 그중 하나를 돌렸으면 이미 갱신돼 있습니다. 바뀐 `bindings.ts` 는 Rust 변경과 함께 커밋합니다.

### 문서 그림 다시 찍기

[사용법](사용법.md)의 그림(`docs/images/*.png`)은 `bench/docs-shots.js` 로 목 모드에서 찍습니다. 자세한 것은 그 파일 머리 주석에 있습니다.

1. 장면 변수 없이 목 서버를 띄웁니다: `VITE_MGIT_MOCK=2000 pnpm -F @mgit/desktop dev:web`
2. Playwright MCP 의 `browser_run_code_unsafe` 를 `filename: "bench/docs-shots.js"` 로 부릅니다. 그림마다 `localStorage` 로 장면을 고르고 새로 고쳐, 창 1400×900·다크로 찍습니다.
3. 결과는 `docs/images/<이름>.png` 입니다. 일부만 찍으려면 파일 안의 `ONLY` 에, 그림을 더하려면 `SHOTS` 에 적습니다.
4. 서버를 끕니다: `lsof -ti tcp:1420 -sTCP:LISTEN | xargs kill`

- 실제 앱 창은 찍지 않습니다. 개발 실행은 설치한 앱의 탭을 복원해 개인 저장소가 보일 수 있습니다(3절).
- 파일 전체가 `async (page) => { … }` 함수 식 하나입니다. Playwright MCP 가 없으면 Playwright 스크립트에서 이 함수에 `page` 를 넘겨 불러도 될 것입니다(해 보지는 않음).

## 8. 문제 해결

### 1420 포트가 이미 쓰임

`pnpm dev` 나 목 모드가 `Error: Port 1420 is already in use` 로 멈추면, 앞서 띄운 서버가 남아 있는 것입니다. 포트는 1420 으로 고정돼 있어 다른 번호로 비켜 가지 않습니다.

```bash
lsof -nP -iTCP:1420 -sTCP:LISTEN               # 누가 쓰는지 보기
lsof -ti tcp:1420 -sTCP:LISTEN | xargs kill    # 끄기
```

### `pnpm dev` 를 했는데 창이 뜨지 않음

- 설치한 mGit 이 떠 있으면 디버그 앱이 그쪽으로 넘기고 끝납니다(3절, 확인 전). 설치한 앱을 끄고 다시 실행합니다.
- 터미널에 `Running` 줄이 아직 없으면 컴파일 중입니다. 첫 빌드는 오래 걸립니다(아래).

### 첫 Rust 빌드가 오래 걸림

처음에는 Tauri 와 의존성을 포함해 컴파일 단위 540여 개를 모두 빌드합니다. 잰 Mac 에서는 41초였고, crate 를 처음 받는 Mac 에서는 내려받는 시간이 더해집니다. 그 뒤로는 고친 crate 만 다시 컴파일합니다.

`target/` 은 금방 커집니다. 클론에서 `pnpm dev`·clippy·test 를 한 번씩 돌린 뒤 9.2GB 였습니다. 자리가 모자라면 `cargo clean` 으로 지웁니다(다음 빌드가 다시 처음부터 컴파일합니다).

### Command Line Tools 가 없음

`xcrun: error: invalid active developer path` 가 나오거나 링커(`cc`)를 찾지 못하면 Command Line Tools 가 없거나 macOS 업데이트 뒤 지워진 것입니다. `xcode-select --install` 로 다시 설치합니다.

### git 이 없거나 버전이 낮음

- `cargo test` 와 앱이 시스템의 git 을 씁니다. 2.45 이상으로 올립니다(`brew install git` 뒤 터미널을 새로 엶).
- 앱에서 보이는 증상과 앱이 git 을 찾는 순서는 [사용법 10.1](사용법/10-문제-해결.md#101-git-이-없거나-버전이-낮을-때)에 있습니다.

### pnpm 버전이 다름

- `pnpm --version` 이 11.20.0 이 아니면 `which -a pnpm` 으로 어느 pnpm 이 먼저 잡히는지 봅니다. corepack 을 쓰려면 `corepack enable pnpm` 을 실행합니다. `corepack` 명령이 없으면 `npm install -g corepack` 으로 설치합니다.
- `pnpm install` 끝에 `Update available! 11.20.0 → …` 와 `corepack use pnpm@…` 안내가 나와도 따르지 않습니다. `corepack use` 는 `package.json` 의 `packageManager` 를 바꿉니다.

### `bindings.ts` 가 바뀌어 보임

`pnpm dev`·`cargo test`·`pnpm gen:ipc` 가 `packages/ipc/src/bindings.ts` 를 다시 씁니다.

- Rust 의 명령·타입을 고쳤다면 정상입니다. Rust 변경과 함께 커밋합니다.
- Rust 를 고치지 않았는데 바뀌었다면 받은 브랜치의 `bindings.ts` 가 Rust 코드보다 뒤처진 것입니다. 바뀐 내용을 확인해 함께 커밋하거나, 그 브랜치를 고친 사람에게 알립니다.

### 터미널에 `reading 'metadata'` 오류가 찍힘

`pnpm dev` 중에 터미널에 `[vite] (client) [Unhandled rejection] TypeError: Cannot read properties of undefined (reading 'metadata')` 가 찍히면, 일반 브라우저가 `http://localhost:1420` 을 열고 있는 것입니다. `pnpm dev` 의 화면은 Tauri 앱 창 안에서만 동작하고, 브라우저에는 Tauri 가 없어 이 오류가 납니다.

- 목 모드를 쓰다 브라우저 탭을 열어 둔 채 `pnpm dev` 를 띄우면, 그 탭이 개발 서버에 다시 연결되며 이 오류가 찍힙니다. 앱 창이 뜨기 전에도 찍히므로 앱 창의 오류가 아닙니다. 그 탭을 닫으면 됩니다.
- 브라우저로 화면을 보려면 목 모드(4절)를 씁니다.

### 앱에 합성 데이터가 보임

`git 2.54.0 (mock)` 같은 글자와 `/mock/…` 경로가 보이면 목 모드로 빌드된 것입니다. 4절 끝의 주의대로 `VITE_MGIT_MOCK` 을 지우고 다시 실행하거나 빌드합니다.
